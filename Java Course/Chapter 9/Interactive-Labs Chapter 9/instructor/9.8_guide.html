COP1800 · Java Programming I · Lab 9.8

The drone deliveries billed at $0.0

Objectives

  • Declare an abstract class that exists only to be extended
  • Declare an abstract method with no body that every concrete subclass must implement
  • Avoid overloading an abstract method by mistake instead of overriding it

Requirements

  1. R1 Delivery is an abstract class, and fee() is an abstract method with no body (the header ends with a semicolon).
  2. R2 DroneDelivery overrides fee() with no parameters, marked @Override, using the distance from getKm().
  3. R3 Running the test program prints exactly what it expects. (verified by the program output)

Before you code: warm-up and model answers

  1. With the starter, drone.receipt() calls fee(). Which fee() runs, and why doesn't the drone's own method run?

    Delivery's placeholder runs and returns 0.0. The drone's method has a double parameter, so it is a different method (an overload) that receipt() never calls.

  2. A placeholder that returns 0.0 compiled fine. What should happen instead when someone forgets a subclass's fee?

    The compiler should refuse the subclass. An abstract fee() in Delivery forces every concrete subclass to implement fee(), so a missing or misspelled one becomes a compile error.

Solution

Delivery.java
public abstract class Delivery
{
    private String orderId;
    private double km;

    public Delivery(String id, double distanceKm)
    {
        orderId = id;
        km = distanceKm;
    }

    public String getOrderId()
    {
        return orderId;
    }

    public double getKm()
    {
        return km;
    }

    public abstract double fee();

    public String receipt()
    {
        return "Order " + orderId + ": " + km + " km, fee $" + fee();
    }
}
DroneDelivery.java
public class DroneDelivery extends Delivery
{
    public DroneDelivery(String id, double distanceKm)
    {
        super(id, distanceKm);
    }

    // $6.0 to launch plus $1.25 per km.
    @Override
    public double fee()
    {
        return 6.0 + 1.25 * getKm();
    }
}

Walkthrough

A class you create only to extend is an abstract class, declared with abstract; no objects of it can be created (p. 352). An abstract method has the keyword abstract, a header and a semicolon, with no braces and no statements (p. 353), and a concrete subclass must implement every inherited abstract method (p. 353). With the placeholder gone, the starter's DroneDelivery doesn't compile, because fee(double) overloads instead of overriding: “Don't mistakenly overload an abstract method instead of overriding it” (p. 381). An abstract class may still have fields, a constructor and ordinary methods such as receipt(), like the abstract Vehicle in the You Do It section (pp. 355–356). When receipt() calls fee(), the subclass's version runs, the same idea as speak() in Figure 9-33 (p. 354).

Messages students see when a check fails

C1 · Delivery is abstract

Write the header as public abstract class Delivery. There is no such thing as a plain delivery, so nobody should be able to write new Delivery(...).

C2 · fee() is abstract, with no body

Replace the placeholder with public abstract double fee();: a header and a semicolon, no braces. Each subclass must then write its own fee.

Hint:

An abstract method ends where its header ends.

C3 · DroneDelivery overrides fee()

Give the drone's method the same header as the abstract one, public double fee() with no parameters, and mark it @Override. With a parameter, it is an overload that nothing calls.

C4 · The drone fee uses getKm()

Get the distance from getKm(): without the parameter, the inherited getter is where the delivery's kilometres come from.

Progressive hints

  1. Make Delivery and its fee() abstract first, then compile. The error names the class that doesn't implement fee().

  2. Compare the drone's fee header with Delivery's abstract one. What is different?

  3. The kilometres are already stored in every Delivery; the subclass reads them with the inherited getter.

Reflection: questions and model answers

  1. Why is a compile error better than a placeholder method that returns 0.0? Use the two weeks of free drone orders in your answer.

    The placeholder let the wrong code run silently, so free orders went out for two weeks. With an abstract fee(), the drone class couldn't have compiled until it had a correct fee(), so the mistake would have been caught before release.

  2. Delivery is abstract, yet it has a constructor and a receipt() method with a body. Why keep them in the abstract class?

    Every kind of delivery has an order ID and a distance and prints the same receipt, so that code is written once and inherited. Only the fee differs, so only fee() is abstract.
