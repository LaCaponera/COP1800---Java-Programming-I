The conference that printed two badges for Priya

Objectives

  • Override toString() so an object prints useful information
  • Tell an overloaded equals(Attendee) apart from an overriding equals(Object), and write the override safely
  • Override hashCode() so equal objects have equal hash codes

Requirements

  1. R1 Attendee overrides toString(), marked @Override, returning the name, a space and the email in angle brackets.
  2. R2 Attendee overrides equals(Object) (and no longer has equals(Attendee)): it returns false for null or an object of another class, and otherwise compares emails ignoring case.
  3. R3 Attendee overrides hashCode() using the email, so two attendees that are equal have the same hash code.
  4. R4 Running the test program prints exactly what it expects. (verified by the program output)

Before you code: warm-up and model answers

  1. priya.equals(priyaAgain) is true with the starter, yet the desk admits Priya twice. Which equals() does the desk's arrived[x].equals(visitor) call, and why?

    It calls Object's equals(Object), because visitor is an Object reference and Attendee only has an overload that takes an Attendee. Object's version is true only for the very same object, so two registrations are never equal.

  2. What should equals() return when an attendee is compared with the String "P-17", and what goes wrong if the method casts the argument to Attendee straight away?

    It should return false. Casting a String to Attendee throws a ClassCastException, so the class must be checked before the cast.

// The venue's check-in desk is shared with the parking and vendor apps,
// so it stores any kind of object.
public class CheckInDesk
{
    private Object[] arrived = new Object[200];
    private int count;

    // Returns false when an equal entry has already checked in.
    public boolean checkIn(Object visitor)
    {
        for (int x = 0; x < count; ++x)
        {
            if (arrived[x].equals(visitor))
                return false;
        }
        arrived[count] = visitor;
        ++count;
        return true;
    }

    public int getCount()
    {
        return count;
    }
}

Solution

Attendee.java
public class Attendee
{
    private String name;
    private String email;

    public Attendee(String fullName, String address)
    {
        name = fullName;
        email = address;
    }

    public String getName()
    {
        return name;
    }

    public String getEmail()
    {
        return email;
    }

    @Override
    public String toString()
    {
        return name + " <" + email + ">";
    }

    // Two registrations are the same person when the emails match,
    // ignoring capital letters.
    @Override
    public boolean equals(Object obj)
    {
        if (obj == this)
            return true;
        if (obj == null || obj.getClass() != getClass())
            return false;
        Attendee other = (Attendee) obj;
        return email.equalsIgnoreCase(other.email);
    }

    @Override
    public int hashCode()
    {
        return email.toLowerCase().hashCode();
    }
}

Walkthrough

Every class extends Object and inherits toString(), equals() and hashCode() (p. 364). The inherited toString() prints the class name, @ and a hash code (p. 365), so overriding it makes logs readable (pp. 365–366). equals(Attendee) has a different parameter list from Object.equals(Object), so it overloads rather than overrides (p. 369); the desk calls equals(Object) and gets Object's version, which is true only for the same object (p. 367). The override follows the recommendations on pp. 369–370: true for the same object, false for null or a different class, cast only after those tests. Note that each early case must return before the cast: in Figure 9-54 as printed, an argument of another class still reaches the cast. Equal objects should have equal hash codes (p. 370); because equals() ignores case, hashCode() uses the lowercase email. a instanceof Attendee is an accepted alternative to the getClass() test.

Messages students see when a check fails

C1 · toString() is overridden

Add @Override public String toString() returning name + " <" + email + ">". println() calls toString() automatically.

C2 · equals() takes an Object

Change the header to public boolean equals(Object obj) (with @Override). Only that exact signature overrides Object's version, which is the one the desk calls.

Hint:

Compare your header with boolean equals(Object obj) in Table 9-2.

C3 · equals() rules out null and other classes

Before casting, return false when the argument is null or not an Attendee: obj == null || obj.getClass() != getClass(). Otherwise a parking pass crashes the desk with a ClassCastException.

C4 · hashCode() is based on the email

Add @Override public int hashCode() that returns email.toLowerCase().hashCode(). Equal attendees must produce equal hash codes, and equals() ignores case, so the hash must too.

Progressive hints

  1. Start with toString(): it's one return statement, and the first line of the output tells you whether it works.

  2. Write equals() in the order the book recommends: the same object, then null, then a different class, and only then the cast (Attendee) obj and the email comparison.

  3. Two emails that differ only in capital letters must give the same hash code, so lowercase the email before calling its hashCode().

Reflection: questions and model answers

  1. The starter's equals(Attendee) worked when you called it yourself but not at the desk. Explain the difference between overloading and overriding equals() using this bug.

    The overload is only chosen when the argument's declared type is Attendee. The desk passes an Object, so Java uses Object's equals(Object). Only an override with the Object parameter replaces the version the desk calls.

  2. Why must hashCode() change whenever equals() changes? What could go wrong if it didn't?

    Equal objects must have equal hash codes. Hash-based collections look an object up by its hash code first, so two equal attendees with different hash codes could both be stored, giving duplicate badges again.
