The audiobook that never got the label fix

Objectives

  • Use the “is a” test to decide which class should inherit from which
  • Tell inheritance (is-a) apart from containment (has-a)
  • Explain how reusing a tested parent class reduces errors

Requirements

  1. R1 AudioBook inherits from Book and declares only what is new: the narrator field and its two methods.
  2. R2 Library does not inherit from Book. It keeps the branch name in its own private String field, and still has books in its Book[] shelf.
  3. R3 Running the test program prints exactly what it expects. (verified by the program output)

Before you code: warm-up and model answers

  1. Say each pair in an “is a” sentence: AudioBook/Book and Library/Book. Which sentence is true?

    “An AudioBook is a Book” is true. “A Library is a Book” is false; a library has books.

  2. With the starter, what would branch.getLabel() return for the Eastside Branch library, and why does the compiler allow the call at all?

    It would return “Eastside Branch by null”. Library extends Book, so it inherits getLabel() and the author field, even though a library has no author.

Walkthrough

An audiobook passes the “is a” test (an AudioBook is a Book, not the other way around), so AudioBook inherits every field and method of Book and only adds the narrator (pp. 330–331). Deleting the copy also deletes the stale getLabel(): the inherited version is the one that was fixed and tested, which is the “reduce errors” benefit on p. 330. A library fails the “is a” test (a library is not a book); it has books, which is containment (aggregation, because the books would still exist if the branch closed; p. 331). The extends keyword is explained in section 9.2; here it is enough to know it is how Java writes “inherits from”.

public class TestLibrary
{

    {

Messages students see when a check fails

C1 · AudioBook inherits from Book

Write the header as public class AudioBook extends Book: an audiobook is a book, so it should receive Book's fields and methods instead of copying them.

Hint:

Which keyword in the Library header already says “inherits from”?

C2 · AudioBook keeps only what is new

Delete the copied title and author fields, their get and set methods, and the old getLabel(). Keep narrator and its two methods. The inherited versions are the tested ones, including the fixed label.

C3 · Library is not a Book

Remove extends Book from the Library header. A library has books; it is not one, so it shouldn't inherit an author or a label.

C4 · Library stores its own name

Declare a field such as private String name; and set it in the constructor. Once Library no longer extends Book, setTitle() isn't available, and the name was never a title anyway.

C5 · getName() returns that field

Return the library's own name field from getName(), not getTitle().

Progressive hints

  1. Start with the “is a” sentence for each class. Only the true sentence earns extends.

  2. After AudioBook extends Book, every line that also appears in Book.java can go. What is left is the narrator.

  3. In Library, replace extends Book with a String field of Library's own: set it in the constructor and return it from getName().

Reflection: questions and model answers

  1. The label bug was fixed once, in Book, yet audiobooks kept the old label. Explain how inheritance would have prevented that.

    With inheritance there is only one getLabel(), the one in Book. Fixing it fixes every subclass at once; a copied method has to be found and fixed separately, and this copy was forgotten.

  2. Why is Library extends Book worse than the duplicated code in AudioBook, even though it saved the programmer some typing?

    It claims a library is a book, so Library inherits an author, a label and setTitle() that make no sense for it, and the compiler can no longer catch misuse. Containment (a name field plus a Book array) models what a library really is.
