COP1800 · Java Programming I · Lab 9.6

The gift card that holds $505.0 on a $500.0 limit

Objectives

  • Explain why information hiding keeps a class's rules in force
  • Decide between private and protected for a field a subclass wants to change
  • Change inherited data through the parent's public methods

Requirements

  1. R1 GiftCard.balance is private: not public, and not protected either.
  2. R2 PromoGiftCard.loadWithBonus() adds the $10.0 bonus by calling load(), so the $500.0 limit applies to it; it never touches balance directly.
  3. R3 Running the test program prints exactly what it expects. (verified by the program output)

Before you code: warm-up and model answers

  1. Trace the starter for loadWithBonus(495.0) on a new card. What is the balance afterwards, and which line broke the rule?

    load(495.0) succeeds and the balance is 495.0; then balance = balance + 10.0 makes it 505.0. That line changes the field directly and skips load()'s limit check.

  2. Besides PromoGiftCard, what else could change balance while it is public?

    Any class at all, for example a test program or a register app writing card.balance = 1000.0 or a negative value, without any of GiftCard's checks.

Starter files

GiftCard.java
public class GiftCard
{
    public static final double MAX_BALANCE = 500.0;
    // TODO (R1): any class can change this, skipping every rule below.
    public double balance;

    public double getBalance()
    {
        return balance;
    }

    // Adds money unless the amount is not positive or the card would
    // go over MAX_BALANCE. Returns whether the money was added.
    public boolean load(double amount)
    {
        if (amount <= 0 || balance + amount > MAX_BALANCE)
            return false;
        balance += amount;
        return true;
    }

    // Takes money off unless the card doesn't have enough.
    public boolean spend(double amount)
    {
        if (amount <= 0 || amount > balance)
            return false;
        balance -= amount;
        return true;
    }
}
PromoGiftCard.java
public class PromoGiftCard extends GiftCard
{
    // Holiday promo: every load of $50.0 or more earns a $10.0 bonus.
    public boolean loadWithBonus(double amount)
    {
        boolean loaded = load(amount);
        if (loaded && amount >= 50.0)
        {
            // TODO (R2): this skips the $500.0 limit that load() enforces.
            balance = balance + 10.0;
        }
        return loaded;
    }
}

Solution

GiftCard.java
public class GiftCard
{
    public static final double MAX_BALANCE = 500.0;
    private double balance;

    public double getBalance()
    {
        return balance;
    }

    // Adds money unless the amount is not positive or the card would
    // go over MAX_BALANCE. Returns whether the money was added.
    public boolean load(double amount)
    {
        if (amount <= 0 || balance + amount > MAX_BALANCE)
            return false;
        balance += amount;
        return true;
    }

    // Takes money off unless the card doesn't have enough.
    public boolean spend(double amount)
    {
        if (amount <= 0 || amount > balance)
            return false;
        balance -= amount;
        return true;
    }
}
PromoGiftCard.java
public class PromoGiftCard extends GiftCard
{
    // Holiday promo: every load of $50.0 or more earns a $10.0 bonus.
    public boolean loadWithBonus(double amount)
    {
        boolean loaded = load(amount);
        if (loaded && amount >= 50.0)
            load(10.0);
        return loaded;
    }
}

Walkthrough

Keeping data private (information hiding) means it can be changed only by the methods you choose and only in ways you control (p. 347), which is how load() guarantees the limit. A subclass can't use its parent's private fields directly (p. 347), so once balance is private, PromoGiftCard must go through load(10.0) like any other class. protected would compile, but it would let the subclass skip the limit again: protected access is meant to be used sparingly, and classes that use their parent's fields directly are “fragile” (p. 347). A child seldom needs protected fields because it can use the parent's public methods (p. 347). The bonus that would exceed the limit is refused by load(); loadWithBonus() still reports true because the customer's own money was loaded.

Messages students see when a check fails

C1 · The balance is private

Declare private double balance;. protected would still let PromoGiftCard (and any future subclass) skip the $500.0 limit, which is exactly what went wrong.

Hint:

Which access level lets only GiftCard's own methods touch the field?

C2 · The bonus goes through load()

Add the bonus with load(10.0) instead of changing balance. load() applies the same $500.0 rule to the bonus as to any other money.

Progressive hints

  1. Change the access specifier of balance first and compile: the error in PromoGiftCard shows exactly which line breaks the rule.

  2. PromoGiftCard already calls one parent method that adds money and checks the limit.

  3. The bonus line becomes a call: load(10.0);. You don't need to know whether it succeeded.

Reflection: questions and model answers

  1. Making balance protected would also let PromoGiftCard compile. Why is private the better choice here?

    With protected, the subclass could still change balance without the limit check, so the bug could come back in this or any future subclass. Private forces every change through load() and spend(), which enforce the rules.

  2. The customer who loads $495.0 doesn't get the $10.0 bonus. Is that the right behaviour? Who decides?

    Yes: the processor rejects cards over $500.0, so a bonus that breaks the limit can't be honoured. That rule belongs to GiftCard; the promo class shouldn't be able to override it.

Extension

Add public boolean refund(double amount) to GiftCard for returned purchases. Should a refund that would push the card over $500.0 be refused, or capped? Write it, then decide whether spend() and refund() should share a private helper method.
