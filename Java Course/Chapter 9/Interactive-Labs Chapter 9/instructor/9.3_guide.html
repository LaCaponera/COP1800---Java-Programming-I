COP1800 · Java Programming I · Lab 9.3

The day pass that costs $25.0 per month

Objectives

  • Override a parent method by writing a child method with the same name and parameter list
  • Tell overriding apart from overloading
  • Use the @Override annotation so the compiler catches a method that doesn't override

Requirements

  1. R1 DayPass overrides rateLabel() (same name, same empty parameter list) and marks it @Override; its label ends in per day.
  2. R2 HourlyDesk keeps its rateLabel(int hours) and also overrides rateLabel(), marked @Override, with a label ending in per hour.
  3. R3 Running the test program prints exactly what it expects. (verified by the program output)

Before you code: warm-up and model answers

  1. With the starter, which class's rateLabel() runs for day.rateLabel(), and why doesn't the DayPass method run?

    Plan's version runs. DayPass's method is named ratelabel with a lowercase l, so it is a different method that doesn't override rateLabel().

  2. HourlyDesk has rateLabel(int hours). Does it override Plan.rateLabel()? What happens when the receipt calls desk.rateLabel()?

    No. Its parameter list is different, so it overloads the method. desk.rateLabel() with no arguments runs Plan's version and prints per month.

Starter files

Plan.java (read-only for students)
public class Plan
{
    private double rate;

    public double getRate()
    {
        return rate;
    }

    public void setRate(double newRate)
    {
        rate = newRate;
    }

    // Members on the standard plan pay by the month.
    public String rateLabel()
    {
        return "$" + rate + " per month";
    }
}
DayPass.java
public class DayPass extends Plan
{
    // TODO (R1): the front desk still prints "per month" for day passes.
    public String ratelabel()
    {
        return "$" + getRate() + " per day";
    }
}
HourlyDesk.java
public class HourlyDesk extends Plan
{
    // Price of a block of hours, for the booking screen.
    public String rateLabel(int hours)
    {
        return "$" + getRate() * hours + " for " + hours + " hours";
    }

    // TODO (R2): a hot desk is rented by the hour, so its label must say
    // "per hour" wherever rateLabel() is called with no arguments.
}

Solution

DayPass.java
public class DayPass extends Plan
{
    @Override
    public String rateLabel()
    {
        return "$" + getRate() + " per day";
    }
}
HourlyDesk.java
public class HourlyDesk extends Plan
{
    // Price of a block of hours, for the booking screen.
    public String rateLabel(int hours)
    {
        return "$" + getRate() * hours + " for " + hours + " hours";
    }

    @Override
    public String rateLabel()
    {
        return "$" + getRate() + " per hour";
    }
}

Walkthrough

A child method overrides a parent method only when both the name and the parameter list match; with a child object, the child's version then runs (p. 337). ratelabel() with a lowercase l is simply a new method, so day.rateLabel() runs the inherited Plan version. rateLabel(int hours) has a different parameter list, so it overloads the parent method and the object has both versions (p. 337). @Override asks the compiler to confirm the method overrides something; on ratelabel() it produces “method does not override or implement a method from a supertype” (pp. 337–339). Using one name, rateLabel(), for every kind of plan is subtype polymorphism (p. 337).

    {

Messages students see when a check fails

C1 · DayPass overrides rateLabel()

Name the method rateLabel exactly as in Plan (capital L, no parameters) and put @Override on the line above it. Java names are case-sensitive, so ratelabel is a different method.

Hint:

Compare the DayPass header with the one in Plan.java letter by letter.

C2 · HourlyDesk overrides rateLabel() too

Add a second method, @Override public String rateLabel() with no parameters. Keep rateLabel(int hours): the booking screen still uses that overload.

C3 · The hot-desk label says per hour

The no-argument label should be built like Plan's, ending in " per hour", for example "$" + getRate() + " per hour".

Progressive hints

  1. Overriding needs two things to match the parent: the method name, letter for letter, and the parameter list.

  2. @Override goes on the line just above the method header. Put it on ratelabel() first and read the compiler's message.

  3. HourlyDesk ends up with two methods named rateLabel: one with an int parameter (overload) and one with none (override).

Reflection: questions and model answers

  1. The starter compiled and ran without a single error, yet two receipts were wrong. How would @Override have changed that?

    With @Override on ratelabel(), the compiler would have refused it because it overrides nothing. The typo would have been caught at compile time instead of on customers' receipts.

  2. HourlyDesk now has two methods named rateLabel. Explain which one runs for desk.rateLabel() and for desk.rateLabel(4), and why both may exist.

    desk.rateLabel() runs the override with no parameters; desk.rateLabel(4) runs the overload with an int. Methods may share a name when their parameter lists differ, and Java picks one by the arguments.
