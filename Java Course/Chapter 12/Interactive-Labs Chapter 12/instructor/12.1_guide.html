COP1800 · Java Programming I · Lab 12.1

The reminder bot that never stops texting

Objectives

  • Explain what makes a method recursive and why a useful one must be able to stop
  • Write a base case that every chain of calls is guaranteed to reach
  • Make each recursive call work on a smaller problem, and count the depth of the recursion

Requirements

  1. R1 Base case: when daysLeft is 0 or less, sendReminders() sends nothing and does not call itself (an overdue book must not start an endless chain).
  2. R2 Recursive case: when daysLeft is greater than 0, it sends one reminder and then calls itself with one day fewer.
  3. R3 It stays recursive: no while or for loop, and calls++ stays the first statement so calls shows how many times the method ran.
  4. R4 Running the test program prints exactly what it expects. (verified by the program output)

Before you code: warm-up and model answers

  1. Trace the starter with sendReminders("Clean Code", 3). What is the second line it prints, and why does a line about 2 days never appear?

    “Reminder: Clean Code is due in 3 day(s)” again. Each call passes the same daysLeft, 3, so the problem never gets smaller and nothing tells it to stop; it repeats until the call stack runs out (StackOverflowError).

  2. In the book's DemoRecursion (Figure 12-3), messageMethod(4) prints four lines. How many times does the method run, and what does the last call do?

    Five times, with 4, 3, 2, 1 and 0. The call with 0 is the base case: the if is false, so it prints nothing and does not call itself again.

Solution

ReminderBot.java
public class ReminderBot
{
    // Counts every call to sendReminders(): the depth of the recursion.
    public static int calls = 0;

    // Sends one reminder for each day left: daysLeft, daysLeft - 1, ..., 1.
    // When no days are left (or the book is overdue) it sends nothing.
    public static void sendReminders(String title, int daysLeft)
    {
        calls++;
        if (daysLeft > 0)
        {
            System.out.println("Reminder: " + title + " is due in "
                + daysLeft + " day(s)");
            sendReminders(title, daysLeft - 1);
        }
    }
}

Walkthrough

This is the book's DemoRecursion pattern (Figure 12-3): an if decides whether to do the work and recurse, and each call passes a smaller value. Two things were missing in the starter: a base case, the case that makes no recursive call (p. 491), and progress toward it. The decisive choice is the condition. daysLeft != 0 or == 0 works for 3, but with -2 the chain runs -2, -3, -4, ... and never reaches 0; every unfinished call waits on the call stack until Java throws StackOverflowError. daysLeft > 0 (or if (daysLeft <= 0) return;) catches every non-positive value. With 3 days the method runs four times (3, 2, 1, 0), the same way messageMethod(4) runs five times on p. 488. A while loop (Figure 12-5) would also work, but this lab practises the recursive form.

Messages students see when a check fails

C1 · A base case that catches 0 and overdue days

Add an if that decides whether this call does any work: send the reminder and recurse only while daysLeft > 0 (or return at once when daysLeft <= 0). Without it, nothing ever stops the chain.

C2 · The base case can't be skipped

A test for exactly 0 misses overdue books: with -2 the calls go -2, -3, -4, ... and never equal 0, so the stack overflows. Test daysLeft > 0 or daysLeft <= 0 instead.

C3 · Each call has one day fewer

The recursive call still passes the same daysLeft, so the problem never gets smaller. Pass daysLeft - 1, the way messageMethod(reps - 1) does in Figure 12-3.

C4 · No post-decrement in the argument

daysLeft-- inside the call passes the old value and subtracts afterwards, so every call still gets the same number. Write daysLeft - 1.

C5 · Repeats by calling itself, not with a loop

This lab practises recursion: remove the loop and let sendReminders() call itself with a smaller daysLeft. (Figure 12-5 shows the loop version for comparison.)

Progressive hints

  1. Ask two questions of every call: when should I stop without calling again? And is the problem I hand on smaller than mine?

  2. Look at messageMethod() in Figure 12-3: an if wraps both the output and the recursive call, and the call passes reps - 1.

  3. The decisive detail is the condition. A test for exactly 0 works for 3 days but not for -2, which skips past 0 forever. Test whether days are left at all (greater than 0), and hand on one day fewer.

Reflection: questions and model answers

  1. Your condition tests whether daysLeft is greater than 0 (or at most 0) rather than equal to 0. Use the overdue book to explain what == 0 would do, and name the error Java reports.

    With -2 the test == 0 is never true: the calls go -2, -3, -4 and never reach the base case. Each unfinished call waits on the call stack, so Java eventually throws StackOverflowError.

  2. Figure 12-5 sends the same messages with a while loop. Give one reason a team might keep the recursive version and one reason to switch to the loop.

    Recursive: it reads as “send one reminder, then handle the smaller problem”, which programmers used to recursion develop quickly. Loop: iteration usually runs faster because there is no overhead of remembering where each call must return.

Extension

Make the base case useful: when daysLeft is exactly 0 print Due today: <title>, and when it is below 0 print Overdue: <title>, still without recursing. Which call in the chain prints it, and does calls change for 3 days?
