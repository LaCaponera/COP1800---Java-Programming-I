The savings calculator the IT team wants as a loop

Objectives

  • Map the parts of a recursive method (base case, recursive step, smaller argument) onto a loop
  • Write an iterative method that gives exactly the same results as a recursive one
  • Weigh recursion against iteration: overhead, call-stack depth and clarity

Requirements

  1. R1 computeSavingsLoop() uses a while or for loop that runs once per year, and does not call itself or computeSavings().
  2. R2 Each year it applies the same calculation as the recursive version, written the same way: total = total + (total * rate) + amt;.
  3. R3 With 0 years it returns the starting total unchanged, as the recursive base case does.
  4. R4 Running the test program prints same: true for every plan, exactly as expected. (verified by the program output)

Before you code: warm-up and model answers

  1. The text on p. 500 says the base case of computeSavings() returns 0. Read the code: what does computeSavings(750, 0, 0.04, 1200) return, and why?

    1. The base case returns total, which is the starting balance when no years are left. It is 0 only when the saver starts with nothing, as in the book's example.

  2. Trace computeSavings(2000, 2, 0.05, 0). What does total become in each call?

    Call 1 (years 2): 0 + 0 + 2000 = 2000. Call 2 (years 1): 2000 + 100 + 2000 = 4100. Call 3 (years 0) is the base case and returns 4100, which is passed back up unchanged.

Solution

SavingsPlan.java
public class SavingsPlan
{
    // Recursive version (Figure 12-21). Leave it as it is.
    public static double computeSavings(double amt, int years,
        double rate, double total)
    {
        if (years == 0)
            return total;
        else
        {
            total = total + (total * rate) + amt;
            return computeSavings(amt, years - 1, rate, total);
        }
    }

    // Iterative version: same parameters, same result, no recursion.
    public static double computeSavingsLoop(double amt, int years,
        double rate, double total)
    {
        while (years != 0)
        {
            total = total + (total * rate) + amt;
            --years;
        }
        return total;
    }
}

Walkthrough

This is Figure 12-24. Each part of the recursive method has a partner in the loop: the base-case test years == 0 becomes the loop condition years != 0, the work in the else becomes the loop body, and the smaller argument years - 1 becomes --years (p. 502 lists the five similarities). Changing the parameters inside the method is safe because Java passes copies of primitive values. With 0 years the loop body never runs and the starting total is returned, which is what the recursive base case does; note that it returns total, not 0 as the text on p. 500 says. The exact form of the calculation matters with double: total += total * rate + amt adds total * rate and amt first, and total * (1 + rate) + amt multiplies differently. Both are equal in algebra, but floating-point rounding makes the 30-year result differ in the last digit, and the test's == catches it. A for (int y = 0; y < years; y++) loop is equally correct.

TestSavingsPlan.java
public class TestSavingsPlan
{
    public static void main(String[] args)
    {
        // amount per year, years, rate, starting total
        double[][] plans = {
            { 2000, 1, 0.05, 0 },
            { 2000, 2, 0.05, 0 },
            { 2000, 30, 0.05, 0 },
            { 500, 10, 0.03, 1000 },
            { 750, 0, 0.04, 1200 }
        };
        for (double[] p : plans)
        {
            int years = (int) p[1];
            double recursive = SavingsPlan.computeSavings(p[0], years, p[2], p[3]);
            double loop = SavingsPlan.computeSavingsLoop(p[0], years, p[2], p[3]);
            System.out.println("$" + (int) p[0] + " a year, " + years + " years at "
                + Math.round(p[2] * 100) + "%, start $" + (int) p[3]);
            System.out.println("  recursive " + recursive);
            System.out.println("  loop      " + loop + "  same: " + (recursive == loop));
        }
    }
}

Messages students see when a check fails

C1 · Uses a loop

Repeat the yearly calculation with a while or for loop that runs once per year, as in Figure 12-24.

C2 · No recursion in the loop version

The iterative version must not call itself or the recursive version; the loop does all the repeating.

C3 · The same calculation, written the same way

Write each year's step exactly as the recursive version does: total = total + (total * rate) + amt;. Regrouped forms such as total += total * rate + amt or total * (1 + rate) + amt round differently with double and can change the last digit.

C4 · Returns the total, not a constant

Return total after the loop. With 0 years the loop doesn't run, and the starting balance comes back unchanged, just like the recursive base case.

Progressive hints

  1. Line up the parts of the recursive method with the parts of a loop: the base-case test becomes the loop condition, the work in the else becomes the loop body, and years - 1 becomes the update.

  2. Figure 12-24 shares five things with the recursive version (p. 502): the same arguments, stop when years reaches 0, the same calculation, years goes down each cycle, and total is returned.

  3. If the 30-year plan prints same: false with matching first digits, the calculation was regrouped. Copy it character for character from the recursive version.

Reflection: questions and model answers

  1. Both versions give identical results. Describe one situation where you would choose the loop and one where you would keep the recursive version.

    Loop: code that runs very often or with many periods; daily interest over 40 years is 14,600 calls, which adds overhead and could overflow the call stack. Recursive: a team that finds “this year, then the rest” clearer, with a small depth such as 30 yearly periods.

  2. The test compares the results with == rather than checking that they are close. What does a match prove, and what would a mismatch in the last digit tell you?

    Identical steps in the same order give bit-identical doubles, so a match proves the loop does exactly the same arithmetic. A last-digit mismatch means the calculation was regrouped, which is equal in algebra but rounds differently in floating point.

Extension

Make the plan monthly: deposit amt / 12 each month at rate / 12 for years * 12 months, in both versions. Then try daily compounding (365 periods a year) for 40 years. Which version still works, and what happens to the other one?
