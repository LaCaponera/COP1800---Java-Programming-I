COP1800 · Java Programming I · Lab 12.2

The playlist tool that crashes on an empty set

Objectives

  • Choose a base case that is the smallest input a recursive method accepts (0! = 1)
  • Follow how waiting calls on the call stack finish in reverse order and combine their results
  • Write a recursive method with two parameters that returns a value

Requirements

  1. R1 factorial() has a base case that 0 reaches: 0! is 1 (p. 492). The recursive case still returns n * factorial(n - 1), with no loop.
  2. R2 factorial() returns a long, so 13 songs (6,227,020,800 orders) is right; an int stops at about 2.1 billion.
  3. R3 arrangements(songs, slots) is recursive and returns a long: with no slots left there is exactly 1 way; otherwise songs times the arrangements of one song fewer into one slot fewer. It does not use factorial() or a loop.
  4. R4 Running the test program prints exactly what it expects. (verified by the program output)

Before you code: warm-up and model answers

  1. Trace the starter's factorial(0). Which values does n take in the first four calls, and why is the base case never reached?

    0, -1, -2, -3. The base case tests n == 1, and counting down from 0 moves away from 1, so the calls never stop until the call stack overflows.

  2. In the book's factorial(4) (Figure 12-12), which call finishes first, and in what order do the waiting calls finish?

    The fifth call, factorial(0), finishes first by returning 1. The waiting calls then finish in reverse order of how they started: factorial(1) returns 1, factorial(2) returns 2, factorial(3) returns 6 and factorial(4) returns 24.

Solution

PlaylistMath.java
public class PlaylistMath
{
    // Returns n!, the number of different orders n songs can be played in.
    public static long factorial(int n)
    {
        if (n == 0)
            return 1;
        else
            return n * factorial(n - 1);
    }

    // Returns the number of ways to fill `slots` positions in order,
    // choosing from `songs` different songs: songs * (songs - 1) * ... (slots factors).
    public static long arrangements(int songs, int slots)
    {
        if (slots == 0)
            return 1;
        else
            return songs * arrangements(songs - 1, slots - 1);
    }
}

Walkthrough

The starter's base case was n == 1. That gives the right 4! = 24, but factorial(0) counts down 0, -1, -2, ... and never meets 1, so the waiting calls pile up on the call stack until it overflows. The base case should be the smallest input the method accepts, and the book defines 0! = 1 (p. 492). The second bug is size: an int holds at most 2,147,483,647, so 13! silently wraps to 1932053504. In long, n * factorial(n - 1) multiplies in long because the call returns a long; 20! is the largest factorial that fits. arrangements() has the same shape with two counters: 0 slots is the base case (one way: do nothing), and each recursive case multiplies the choices for the first slot by the arrangements of the rest. When there are more slots than songs, the chain reaches songs == 0 and multiplies by 0, so 3 of 2 is correctly 0. Dividing two factorials (factorial(songs) / factorial(songs - slots)) would give the same answers here but overflows as soon as songs passes 20.

Messages students see when a check fails

C1 · 0 reaches the base case

factorial(0) counts down 0, -1, -2, ... and never meets n == 1. Make the base case n == 0 returning 1: the book defines 0! as 1, and it is the smallest set the tool accepts.

C2 · Still recursive: n times the smaller factorial

Keep the recursive case as n * factorial(n - 1): each call solves a factorial one smaller.

C3 · factorial() returns a long

Change the return type to long. An int holds at most 2,147,483,647, so 13! (6,227,020,800) wraps around to a wrong number without any error.

C4 · No loop in factorial()

Keep factorial() recursive: the base case and n * factorial(n - 1) do the repeating.

C5 · arrangements() has a base case

Start with the case that needs no recursion: when slots is 0 there is exactly one way to fill no positions, so return 1.

C6 · One song and one slot fewer each call

The first slot has songs choices; the rest is the same problem with one song and one slot fewer. Return songs * arrangements(songs - 1, slots - 1).

C7 · No factorials or loops in arrangements()

Solve it with its own recursion. factorial(songs) / factorial(songs - slots) overflows long once songs passes 20, even when the answer is small.

Progressive hints

  1. There are two separate problems in factorial(): one is where the countdown stops, the other is how big the answer gets. Fix one, run, then fix the other.

  2. What is 0! by definition (p. 492)? Make that the base case. For the size problem: the largest int is about 2.1 billion; which integer type holds 6,227,020,800?

  3. arrangements() has the shape of factorial() with two counters: no slots left means exactly one way; otherwise multiply the choices for the first slot by the arrangements of the remaining songs into the remaining slots.

Reflection: questions and model answers

  1. Both n == 1 and n == 0 give 4! = 24. Why is n == 0 the better base case for this tool?

    0! is defined as 1 and 0 is a real input: an empty set has exactly one order. With n == 1, factorial(0) counts down past 1 and never stops. A base case should be the smallest input the method accepts.

  2. Even with long, factorial(21) returns -4249290049419214848. What is happening, and why doesn't Java report an error?

    21! is larger than the biggest long (about 9.2 × 10^18), so the multiplication overflows and wraps around. Java's integer arithmetic doesn't check for overflow; it silently keeps the low bits, so the result is wrong but no error appears.

Extension

Return Math.multiplyExact(n, factorial(n - 1)) instead of n * factorial(n - 1). It throws an ArithmeticException when the result overflows instead of returning a wrong number. What is the largest n that still works, and which songs count makes it throw?
