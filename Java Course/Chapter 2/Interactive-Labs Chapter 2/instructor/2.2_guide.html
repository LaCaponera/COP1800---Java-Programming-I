The router's data meter

Objectives

  • Choose byte, short, int or long from a variable's largest possible value
  • Recognize integer overflow when a product is too large for an int
  • Write a long literal with the uppercase L suffix
  • Explain the compiler's "possible lossy conversion" and "integer number too large" messages

Requirements

  1. R1 devices and daysInCycle use the smallest type that holds 32 and 31.
  2. R2 dailyMegabytes uses the smallest type that holds 30,000; monthlyMegabytes (up to 31 × 30,000) stays an int.
  3. R3 monthlyBytes is a long, and the multiplication that produces it is done with a long operand, so it can't overflow.
  4. R4 planCapBytes is a long initialized with a literal ending in an uppercase L, and it is printed as the last line.
  5. R5 The meter matches the screen above exactly. (verified by the program output)

Before you code: warm-up and model answers

  1. The starter's int monthlyBytes = monthlyMegabytes * 1000000; compiles. Will it print 855000000000? Explain why or why not.

    No. 855,000 × 1,000,000 is 855 billion, but an int can hold only up to 2,147,483,647. Both operands are int, so the product overflows: the program still runs but prints a meaningless number, possibly negative.

  2. A long can hold 1,200,000,000,000, yet long planCapBytes = 1200000000000; doesn't compile. Why?

    A whole-number literal is an int by default, and 1,200,000,000,000 is too large to be an int, so the compiler rejects the literal itself before it ever reaches the long. Adding L makes the literal a long.

Solution

DataMeter.java
public class DataMeter
{
    public static void main(String[] args)
    {
        byte devices = 7;
        byte daysInCycle = 30;
        short dailyMegabytes = 28500;
        int monthlyMegabytes = dailyMegabytes * daysInCycle;

        long monthlyBytes = monthlyMegabytes * 1_000_000L;

        long planCapBytes = 1_200_000_000_000L;

        System.out.println("Devices on network: " + devices);
        System.out.println("Billing cycle: " + daysInCycle + " days");
        System.out.println("Average per day: " + dailyMegabytes + " MB");
        System.out.println("Month so far: " + monthlyMegabytes + " MB");
        System.out.println("Month so far: " + monthlyBytes + " bytes");
        System.out.println("Plan cap: " + planCapBytes + " bytes");
    }
}

Walkthrough

32 and 31 fit in a byte (up to 127) and 30,000 fits in a short (up to 32,767), but 31 × 30,000 = 930,000 needs an int. 855000 * 1000000 is 855 billion, far past the int limit of 2,147,483,647, so with two int operands the product wraps around and even the sign is lost. Declaring the result long is not enough on its own: the multiplication must already be done in long, which the L on 1_000_000L guarantees. The plan cap needs L because a literal without it is an int, and 1.2 trillion is too large to be one.

Messages students see when a check fails

C1 · devices and daysInCycle are bytes

Both maximums (32 devices, 31 days) are below 127, so byte is the smallest type that holds them. Change int to byte in both declarations.

Hint:

Table 2-2 lists the largest value of each integer type.

C2 · dailyMegabytes is a short; monthlyMegabytes stays an int

30,000 is too big for a byte but fits in a short (up to 32,767). The monthly total can reach 31 × 30,000 = 930,000, which is too big for a short, so it stays an int.

C3 · monthlyBytes is a long computed in long

Declare monthlyBytes as a long and write the factor as a long literal: 1_000_000L or 1000000L. With two int operands Java multiplies in int and overflows before the result reaches the long variable.

Hint:

Run it with only the type changed to long. Is the number right yet?

C4 · The plan cap is a long literal with an uppercase L

Declare long planCapBytes and end the number with an uppercase L. Without the suffix the literal is an int, and the compiler reports "integer number too large". Lowercase l works but looks like the digit 1.

C5 · The plan cap is printed

Add a last output line in the same pattern as the others: the text Plan cap: , the variable, then bytes.

Progressive hints

  1. For each variable, read its largest possible value in the scenario, then find the first row of Table 2-2 whose maximum is at least that big.

  2. An overflowed result doesn't cause an error: the program runs and prints a wrong number. Compare 855 billion with the largest int.

  3. The type of a calculation is decided by its operands, not by the variable that receives it. One long operand is enough to make the multiplication long.

Reflection: questions and model answers

  1. You changed monthlyBytes to long. Why was that not enough without the L on the factor?

    Java decides the type of monthlyMegabytes * 1000000 from its operands: both are int, so the multiplication happens in int and overflows. Only then is the wrong result stored in the long. Making one operand a long makes Java multiply in long, which has room for 855 billion.

  2. The course's examples normally use int for whole numbers. Why did this program use byte and short, and when would you not bother?

    The program runs on a router with very little memory, and byte and short use 1 and 2 bytes instead of 4. On a PC, saving a few bytes rarely matters, so int is simpler; small types are worth it on small devices or when there are very many values.
