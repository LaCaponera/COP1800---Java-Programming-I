The help desk that answers URGENT tickets in 0 hours

Objectives

  • Use an enumerated type's constants in a switch structure
  • Compare enum constants by their declared order with compareTo(), not by their spelling
  • Build output from values() and ordinal() so it follows the enum when the enum changes
  • Explain what makes an enum type-safe compared with int or String codes

Requirements

  1. R1 responseHours() chooses the hours with a switch on the Priority, with a case for each priority (LOW may be the default), and no arithmetic on ordinal().
  2. R2 moreUrgent() compares the two constants by their declared order with compareTo() (or their ordinal() values), not by their names.
  3. R3 menu() builds the list from Priority.values(), numbering each constant with ordinal() + 1, separated by commas: 1 LOW, 2 NORMAL, 3 HIGH, 4 URGENT.
  4. R4 Running the test program prints exactly what it expects. (verified by the program output)

Before you code: warm-up and model answers

  1. What does Priority.URGENT.ordinal() return, and what does the starter's formula 72 - p.ordinal() * 24 give for it?

    ordinal() returns 3, URGENT's position counting from 0. The formula gives 72 - 72 = 0 hours.

  2. Is Priority.LOW.compareTo(Priority.HIGH) negative, 0 or positive? And "LOW".compareTo("HIGH")?

    Priority.LOW.compareTo(Priority.HIGH) is negative, because LOW is declared before HIGH. "LOW".compareTo("HIGH") is positive, because L comes after H in the alphabet.

Solution

HelpDesk.java
public class HelpDesk
{
    // Hours the desk promises to answer within:
    // URGENT 1, HIGH 4, NORMAL 24, LOW 72.
    public static int responseHours(Priority p)
    {
        int hours = 72;
        switch(p)
        {
            case URGENT:
                hours = 1;
                break;
            case HIGH:
                hours = 4;
                break;
            case NORMAL:
                hours = 24;
                break;
            case LOW:
                hours = 72;
                break;
        }
        return hours;
    }

    // Whichever of the two priorities is more urgent (a, if they are equal).
    public static Priority moreUrgent(Priority a, Priority b)
    {
        if(a.compareTo(b) >= 0)
            return a;
        return b;
    }

    // The menu agents see: every priority with its number, starting at 1.
    public static String menu()
    {
        String text = "";
        for(Priority p : Priority.values())
        {
            if(p.ordinal() > 0)
                text += ", ";
            text += (p.ordinal() + 1) + " " + p;
        }
        return text;
    }
}

Walkthrough

An enumerated type has a fixed set of constants in a declared order, and the first position is 0, as in an array (p. 312). ordinal() returns that position, which is not a quantity, so arithmetic on it produced 48, 24 and 0 hours. A switch on the enum states each promise explicitly (Figure 8-42); the case labels are the constant names alone. compareTo() on enum constants compares declared positions (Table 8-4), so a.compareTo(b) >= 0 means a is at least as urgent as b; comparing toString() values compares spelling instead. Despite the example on p. 314, the operators < and > do not compile with enum constants in Java (bad operand types for binary operator): use compareTo() or compare ordinal() values. values() returns an array of the constants in declared order (Table 8-5), so the menu now follows the enum automatically. valueOf() turns typed text into a constant, which is how the test program converts "high".

Messages students see when a check fails

C1 · responseHours() uses a switch on the priority

Use switch(p) with a case for each constant (case URGENT:, case HIGH:, ...) and the hours the desk promises. A constant's position is not a number of hours: URGENT is position 3, and the formula turned that into 0 hours.

C2 · moreUrgent() compares declared order

Compare the constants themselves: a.compareTo(b) >= 0 is true when a is declared at the same place as b or later, so it is at least as urgent. Comparing toString() values compares spelling, and "LOW" comes after "HIGH" alphabetically.

C3 · menu() is built from Priority.values()

Loop over Priority.values() and add each constant as its ordinal() + 1, a space and the constant, with a comma and a space between items. A typed string can't notice when a constant is added to the enum; values() always does.

Progressive hints

  1. You can switch on an enum variable. The case labels are the constant names alone, such as case LOW: (older Java versions reject Priority. in front of them).

  2. Every enum constant has a compareTo() method that compares positions in the declaration: negative when the calling constant comes first, 0 when they are the same, positive when it comes later.

  3. Priority.values() returns an array of all the constants in declared order, so an enhanced for loop can visit them. Put the comma before every item except the first.

Reflection: questions and model answers

  1. Why is arithmetic on ordinal() fragile even when the numbers happen to come out right? What would 72 - p.ordinal() * 24 give URGENT if someone inserted CRITICAL between HIGH and URGENT?

    ordinal() is only a position, so any formula built on it changes meaning when the list changes. With CRITICAL inserted, URGENT moves to position 4 and the formula gives 72 - 96 = -24 hours.

  2. Before this enum existed, priorities were int codes 1 to 4. Name two mistakes the Priority type now makes impossible.

    A ticket can't get an invalid code such as 7 or 0, because only the four constants exist. And nobody can do meaningless arithmetic, such as adding two priorities, because the compiler rejects + on enum values: the type is type-safe.

  3. Your menu() picked up URGENT with no extra work. Which method in HelpDesk would still need editing if a new priority were added, and why is that a good thing?

    responseHours(), because a new priority needs its own promised hours, a business decision the code can't guess. The switch is the one place where that decision is written down.

Extension

In a copy of the project, add CRITICAL between HIGH and URGENT in Priority.java, with a promise of 2 hours. Which methods need changes? Does moreUrgent() still work without any?
