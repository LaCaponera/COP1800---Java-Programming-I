The visit counter that starts over every morning

Objectives

  • Tell volatile storage (RAM, variables) apart from nonvolatile storage (files on a disk)
  • Keep a value that must survive a restart in a file instead of a field
  • Name the everyday file tasks a program performs: check, open, read, write, close, delete

Requirements

  1. R1 VisitCounter keeps no count in a field: the total lives only in the file that store manages.
  2. R2 recordVisit() starts from the saved total, adds 1, saves the new total with store.save(), and returns it.
  3. R3 getTotal() returns the saved total, or 0 when no file exists yet; reset() makes the saved total 0 (delete the file, or save 0).
  4. R4 Running the test program prints exactly what it expects. (verified by the program output)

Before you code: warm-up and model answers

  1. Which storage holds the starter's visits value, and what happens to that value when main() ends?

    RAM, because it is a field of an object. RAM is volatile, so the value is lost when the program ends; the next run starts a new object with visits at 0.

  2. With the starter, what does the test program print after “Tuesday: the tablet restarted”? Why doesn't the Tuesday object know about Monday's 3 visits?

    “Total so far: 0” and “Visit 1”. Each VisitCounter object has its own visits field, and Monday's object (and its field) is not where Tuesday's object looks.

Starter files

TextStore.java (read-only for students)
import java.nio.file.*;
import java.io.*;

// Keeps one line of text in a file on disk: nonvolatile storage.
// Sections 11.2 to 11.5 explain the code inside these methods.
public class TextStore
{
    private Path file;

    public TextStore(String fileName)
    {
        file = Paths.get(fileName);
    }

    // true when the file is on the disk
    public boolean exists()
    {
        return Files.exists(file);
    }

    // Returns the line saved in the file.
    public String load() throws IOException
    {
        BufferedReader reader = new BufferedReader(
            new InputStreamReader(Files.newInputStream(file)));
        String line = reader.readLine();
        reader.close();
        return line;
    }

    // Replaces the file's contents with this text.
    public void save(String text) throws IOException
    {
        BufferedWriter writer = new BufferedWriter(
            new OutputStreamWriter(Files.newOutputStream(file)));
        writer.write(text, 0, text.length());
        writer.close();
    }

    // Removes the file from the disk (nothing happens if it isn't there).
    public void delete() throws IOException
    {
        Files.deleteIfExists(file);
    }
}

Solution

VisitCounter.java
import java.io.IOException;

public class VisitCounter
{
    private TextStore store;

    public VisitCounter(String fileName)
    {
        store = new TextStore(fileName);
    }

    // Records one visit and returns the new total.
    public int recordVisit() throws IOException
    {
        int visits = getTotal() + 1;
        store.save("" + visits);
        return visits;
    }

    // Returns the total without changing it.
    public int getTotal() throws IOException
    {
        if (!store.exists())
            return 0;
        return Integer.parseInt(store.load());
    }

    // Starts a new month at 0 visits.
    public void reset() throws IOException
    {
        store.delete();
    }
}

Walkthrough

The visits field is in RAM, which is volatile storage: it disappears when the program ends, and a new object starts with its own new field set to 0 (p. 441). A file is nonvolatile, so the total survives a restart (pp. 441–442). getTotal() is the one place that reads the file; it checks store.exists() first because there is nothing to read on the very first visit (determining whether a file exists is the first task in the list on p. 443). recordVisit() reuses getTotal(), so the read logic is written once. reset() can delete the file, which getTotal() then reads as 0, or save "0". Note the book's point that temporary and permanent describe volatility, not time: the field lasted all day, but it was still temporary (p. 441).

Messages students see when a check fails

C1 · No count kept in a field

Delete the int field. Anything stored in a field is in RAM and is lost at the next restart; the total must come from the file every time.

C2 · recordVisit() saves the new total

Call store.save(...) with the new total so it reaches the disk. save() takes a String, so pass something like "" + visits.

C3 · recordVisit() starts from the saved total

Before adding 1, get the total that is already saved (call getTotal()), or Tuesday's first visit becomes visit 1 again.

C4 · getTotal() reads the file

Read the saved text with store.load() and turn it into an int with Integer.parseInt().

C5 · getTotal() handles the first visit

On the very first visit there is no file yet, and load() would fail. Check store.exists() first and return 0 when it is false.

C6 · reset() changes the saved total

Resetting a variable doesn't touch the disk. Delete the file with store.delete() (getTotal() then reads 0) or save "0".

Progressive hints

  1. Which line is the only place the starter keeps the count? Where does that memory go when the program ends?

  2. Write getTotal() first: if store.exists() is false nothing has been saved yet, so the total is 0; otherwise convert store.load() with Integer.parseInt().

  3. recordVisit() needs three steps: total from getTotal(), plus 1, then store.save() with that number as a String. Return the same number.

Reflection: questions and model answers

  1. The tablet stays on for ten hours a day. Does that make the visits field permanent storage? Use the book's meaning of temporary and permanent.

    No. Temporary and permanent describe volatility, not time. The field is in RAM, so it is lost when power or the program goes, however long it lasted; the file persists because it is on nonvolatile storage.

  2. Your VisitCounter reads the file on every call to getTotal(). Name one cost of that design and one reason it is still the right choice here.

    Reading a disk is slower than reading a variable. But a visit happens a few hundred times a day, and reading the file each time guarantees the total is correct after any restart or crash.

Extension
