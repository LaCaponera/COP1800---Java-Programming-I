The cleanup tool that only says “IO exception”

Objectives

  • Create a Path without hard-coding one operating system's delimiter
  • Use getNameCount(), getName() and getFileName() to take a Path apart
  • Delete with Files.delete() and catch NoSuchFileException and DirectoryNotEmptyException separately

Requirements

  1. R1 pathFor() builds the Path without typing a delimiter: use getSeparator(), or give the folder and the name to Paths.get() as two arguments.
  2. R2 Each report line starts with the item's file name only (getFileName()), not the whole path.
  3. R3 remove() catches NoSuchFileException and DirectoryNotEmptyException before IOException and returns the exact messages above.
  4. R4 Running the test program prints exactly what it expects. (verified by the program output)

Before you code: warm-up and model answers

  1. On a Mac, what do getNameCount() and getFileName() return for the starter's Paths.get("scratch" + "\\" + "old.log")? Why?

    1 and scratch\old.log. On UNIX the backslash isn't a delimiter, so the whole string is one name in the current folder.

  2. According to p. 447, which exception does Files.delete() throw for a file that doesn't exist, and which for a folder that still has files in it?

    NoSuchFileException for the missing file, DirectoryNotEmptyException for the folder that isn't empty.

Solution

Cleaner.java
import java.nio.file.*;
import java.io.IOException;

public class Cleaner
{
    private String folder;

    public Cleaner(String folderName)
    {
        folder = folderName;
    }

    // Builds the Path of one item inside the folder.
    public Path pathFor(String name)
    {
        FileSystem fs = FileSystems.getDefault();
        return fs.getPath(folder + fs.getSeparator() + name);
    }

    // Tries to delete one item and returns one line for the cleanup report.
    public String remove(String name)
    {
        Path item = pathFor(name);
        String label = item.getFileName().toString();
        try
        {
            Files.delete(item);
            return label + ": deleted";
        }
        catch (NoSuchFileException e)
        {
            return label + ": not found, nothing to delete";
        }
        catch (DirectoryNotEmptyException e)
        {
            return label + ": folder is not empty, kept";
        }
        catch (IOException e)
        {
            return label + ": could not delete";
        }
    }
}

Walkthrough

Windows uses \ as the path delimiter and UNIX uses / (p. 442), so a hard-coded "\\" makes a one-element Path on a Mac. FileSystem.getSeparator() returns the right delimiter for the system the program runs on (p. 444); Paths.get(folder, name) does the same job by joining its arguments with that separator. Either way getNameCount() is 2 and getName(0) is the folder (pp. 444–445). getFileName() returns the last element, which keeps the report the same on every system. Files.delete() throws NoSuchFileException for a missing item and DirectoryNotEmptyException for a folder with files in it (p. 447); both are subclasses of IOException, so their catch blocks must come first or the compiler reports them as already caught. Calling delete() and catching the exception, instead of checking Files.exists() first, also avoids the TOCTTOU bug on p. 447.

Messages students see when a check fails

C1 · pathFor() uses the system's separator

Build the Path with FileSystems.getDefault().getSeparator() between the folder and the name, or call Paths.get(folder, name). Both use the right delimiter on Windows and on a Mac.

C2 · No Windows-only backslash

Remove the "\\" delimiter. A backslash separates folders only on Windows; on macOS and Linux it becomes part of the file name.

C3 · Report lines use the file name

Start each line with item.getFileName() instead of item. The full path prints differently on every system; the name is what the reader needs.

C4 · Missing items get their own catch

Add catch (NoSuchFileException e) before catch (IOException e) and return <name>: not found, nothing to delete.

C5 · Non-empty folders get their own catch

Add catch (DirectoryNotEmptyException e) before catch (IOException e) and return <name>: folder is not empty, kept.

Reflection: questions and model answers

  1. Why does the compiler reject catch (IOException e) placed before catch (NoSuchFileException e)?

    NoSuchFileException is a subclass of IOException, so the first catch would already handle it and the second could never run. Java reports that unreachable catch as an error; specific exceptions must come first.

  2. A teammate suggests checking Files.exists(item) before calling Files.delete(item) so the exception never happens. What problem from p. 447 does that leave open?

    A TOCTTOU bug: the file can disappear (or appear) between the time of check and the time of use, so delete() can still fail. Calling delete() and catching NoSuchFileException handles that case.
