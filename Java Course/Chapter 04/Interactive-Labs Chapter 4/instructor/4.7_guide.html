The marina's empty moorings

Objectives

  • Explain how one copy of an instance method reaches the right object's fields through the implicit this reference
  • Recognize when a parameter shadows a field, and reach the field with this.field
  • Call one constructor from another with this(...) to remove repeated code

Requirements

  1. R1 The three-parameter constructor keeps its parameter names and stores each one in its field with the explicit this reference.
  2. R2 The other two constructors each call another constructor with this(...); only the three-parameter constructor assigns the fields.
  3. R3 Running the test program prints exactly what it expects. (verified by the program output)

Before you code: warm-up and model answers

  1. In the first constructor, which slipNumber does slipNumber = slipNumber; mean on each side of the =? What does describe() print for the Sea Lark?

    Both sides mean the parameter, which shadows the field because it is closer in scope. The field is never assigned and keeps its default, so it prints Slip 0: null at $0.0 a night.

  2. describe() uses slipNumber without this, and it reaches the field. Why does it work there but not in the constructor?

    describe() has no parameter or local variable named slipNumber, so the name means the field of the object the method was called with, through the implicit this reference. In the constructor, the parameter hides the field.

Solution

Mooring.java
public class Mooring
{
    private int slipNumber;
    private String boatName;
    private double nightlyRate;

    public Mooring(int slipNumber, String boatName, double nightlyRate)
    {
        this.slipNumber = slipNumber;
        this.boatName = boatName;
        this.nightlyRate = nightlyRate;
    }

    // Visitors without a reservation: the guest dock, slip 99.
    public Mooring(String name)
    {
        this(99, name, 45.0);
    }

    // A guest-dock slip held for a boat whose name isn't known yet.
    public Mooring()
    {
        this("TBA");
    }

    public String describe()
    {
        return "Slip " + slipNumber + ": " + boatName + " at $"
            + nightlyRate + " a night";
    }
}

Walkthrough

Inside the first constructor, the parameters slipNumber, boatName and nightlyRate are closer in scope than the fields with the same names, so they shadow them: slipNumber = slipNumber; copies the parameter onto itself, and the fields keep their defaults, 0, null and 0.0. this.slipNumber names the field of the object being constructed. describe() needs no this because it has no local variable with those names; the reference is there implicitly. The short constructors now pass their values to another constructor with this(...), which must be the first statement; the solution chains Mooring() to Mooring(String), and this(99, "TBA", 45.0) is equally correct. A change to the guest-dock rate is now one edit.

Test program

Students run it in an IDE and paste the output into the page.

TestMooring.java
public class TestMooring
{
    public static void main(String[] args)
    {
        Mooring reserved = new Mooring(12, "Sea Lark", 62.5);
        Mooring visitor = new Mooring("Blue Heron");
        Mooring held = new Mooring();

        System.out.println(reserved.describe());
        System.out.println(visitor.describe());
        System.out.println(held.describe());
    }
}

Slip 99: Blue Heron at $45.0 a night

Messages students see when a check fails

C1 · The fields are reached with this

Write this. before each field on the left of the =: this.slipNumber = slipNumber; and so on. Without it, both names mean the parameter, which shadows the field, and the assignment does nothing.

Hint:

Keep the parameter names: the reading's fix is this, not renaming.

C2 · Two constructors call another with this(...)

Replace the assignments in Mooring(String name) and Mooring() with one statement each: this(...) with the arguments for another constructor. Then only the three-parameter constructor assigns fields, so a change to the guest dock is made once.

Hint:

What slip, name and rate does a visitor's mooring hand over?

Progressive hints

  1. Inside a method, a parameter with the same name as a field hides (shadows) the field. Something has to tell the compiler you mean the object's own field.

  2. One constructor can call another constructor of the same class with the word this followed by an argument list. It must be the first statement.

  3. The guest-dock values become arguments: which slip number, name and rate does each short constructor hand to the one that does the work?

Reflection: questions and model answers

  1. The harbor master changes the guest-dock rate to $48.0. How many places do you edit in your version, and how many in the starter?

    One in my version, the this(...) call that passes 45.0 (in the solution's chain, only Mooring(String)). In the starter, two constructors typed 45.0, and missing one would give visitors and held slips different rates.

  2. Only one copy of describe() exists in memory, however many moorings there are. How does it print slip 12 for one object and slip 99 for another?

    Every call to a nonstatic method passes the calling object's address as the hidden this reference, so the single copy of describe() reads the fields of whichever object it was called with.
