The shelter board

Objectives

  • Distinguish a class (the blueprint) from its objects (instances)
  • Create objects whose attributes hold different values (different state)
  • Ask an object to act by calling its methods
  • Explain how encapsulation protects an object's data

Requirements

  1. R1 Create two more Dog objects named bowser and roxy with the morning values above (Roxy's shot status is "Due").
  2. R2 The morning board describes Ginger, Bowser and Roxy, in that order.
  3. R3 After the evening heading, change Ginger and Roxy by calling their methods (haveBirthday(), updateShots()): don't create replacement dogs and don't touch their data directly.
  4. R4 The evening board describes all three dogs again, in the same order, showing their new state. (verified by the program output)

Before you code: warm-up and model answers

  1. Read Dog.java. Name the four attributes every Dog has, and the three methods every Dog can perform. Which are like adjectives, and which like verbs?

    The attributes are name, age, breed and shotStatus; they describe a dog, like adjectives. The methods are haveBirthday(), updateShots() and describe(); they are actions, like verbs.

  2. All four attributes are marked private. What does that prevent ShelterBoard from doing, and how can the board still change a dog's age?

    Code outside Dog can't read or assign those fields directly, so ShelterBoard can't write something like ginger.age = 7. It can still change the age by calling a public method, haveBirthday(), which runs inside Dog and is allowed to update the field. That is encapsulation.

Dog.java (read-only for students)
public class Dog
{
    // Attributes: every Dog has these four properties.
    private String name;
    private int age;
    private String breed;
    private String shotStatus;

    // Creates a Dog with its starting state.
    public Dog(String name, int age, String breed, String shotStatus)
    {
        this.name = name;
        this.age = age;
        this.breed = breed;
        this.shotStatus = shotStatus;
    }

    // Methods: what every Dog can do.
    public void haveBirthday()
    {
        age = age + 1;
    }

    public void updateShots()
    {
        shotStatus = "Up to date";
    }

    public void describe()
    {
        System.out.println(name + " | age " + age + " | " + breed + " | shots: " + shotStatus);
    }
}

Solution

ShelterBoard.java
public class ShelterBoard
{
    public static void main(String[] args)
    {
        System.out.println("Shelter board - morning");
        Dog ginger = new Dog("Ginger", 6, "Akita", "Up to date");
        ginger.describe();

        Dog bowser = new Dog("Bowser", 2, "Retriever", "Up to date");
        Dog roxy = new Dog("Roxy", 1, "Beagle", "Due");
        bowser.describe();
        roxy.describe();

        System.out.println("Shelter board - evening");
        ginger.haveBirthday();
        roxy.updateShots();
        ginger.describe();
        bowser.describe();
        roxy.describe();
    }
}

Walkthrough

Dog is written once; ginger, bowser and roxy are three instances of it. They share the same attributes and methods but hold different values, which is their state. Because the attributes are private (encapsulation), the board can't assign ginger.age directly; it asks the object to change itself with haveBirthday(). Creating a new 7-year-old Ginger would print the same text but would model a different dog, not the same dog getting older.

Messages students see when a check fails

C1 · Bowser is created with his morning state

Follow the pattern of the Ginger line: Dog bowser = new Dog(...) with the name, age, breed and shot status in the same order as the Dog constructor's parameters (look at Dog.java).

Hint:

The order of the values matters: name, age, breed, shot status.

C2 · Roxy is created with her shots due

Create roxy the same way with "Roxy", 1, "Beagle" and "Due". Text values go in quotation marks; the age is a number, so it doesn't.

C3 · The morning board describes all three dogs

Before the evening heading, ask each object to describe itself: the object's name, a dot, then the method name with parentheses, in the order Ginger, Bowser, Roxy.

C4 · Ginger and Roxy change through their own methods

Call haveBirthday() on ginger and updateShots() on roxy. Don't assign their fields (they're private: only Dog's own methods may change them) and don't replace them with new objects, which would be different dogs rather than the same dogs changing.

Hint:

Methods are the verbs of an object. Which verb in Dog.java makes a dog one year older?

C6 · The same dogs change: no replacement objects

Each dog should be created once. Building a second Ginger (or Roxy) with new values makes a different object that only looks the same; ask the existing object to change with its method instead.

C5 · The evening board describes all three again

After the evening heading and the two changes, describe Ginger, Bowser and Roxy again, in that order, so the desk sees each dog's current state.

Progressive hints

  1. Open the Dog.java tab first. Find the four attributes and the three methods. Which of them could the shelter board use directly, and which are hidden?

  2. Each new dog needs one line shaped like the Ginger line: a type, a name for the object, =, new, the class name, and the starting values in the constructor's order.

  3. Changing state is a request to the object, not an assignment: write the object's name, a dot and the method that makes the change. Do both changes before the evening describe() calls, or the board will show the morning values.

Reflection: questions and model answers

  1. ginger, bowser and roxy all come from the same class. What is the same about them, and what makes each one different?

    They share the same attributes and methods because they were all built from the Dog blueprint. What differs is the values stored in those attributes, each object's state: different names, ages, breeds and shot status.

  2. A classmate replaced the birthday call with ginger = new Dog("Ginger", 7, "Akita", "Up to date");. The output looks identical. Why is calling haveBirthday() still the better design?

    The new statement throws away the original object and builds a different dog that happens to have the same values, and the board has to know Ginger's breed and shot status to do it. haveBirthday() changes the existing object's state through its own method, so the rule for ageing lives in one place inside Dog, and the board doesn't need to know or retype the other attributes.

Extension

Add a fourth dog that arrives in the evening. Then, in your own copy of Dog.java, add a method adopt() that sets a new attribute status to "Adopted". Which other method must change so the board shows it?
