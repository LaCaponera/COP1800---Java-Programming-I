The audit that thinks a Jukebox is a control

Objectives

  • Describe how JComponent, Container, Component, Window, Frame and JFrame are related
  • Explain why every Swing control is also a container, and why a JFrame is not a JComponent
  • Use instanceof to classify GUI objects by type instead of guessing from a class name

Requirements

  1. R1 isSwingControl() returns true exactly for objects that descend from JComponent. It must not look at the class name.
  2. R2 isContainer() returns true for anything that can hold other components, that is, any Container (not only frames).
  3. R3 isWindow() returns true for top-level windows: objects that descend from Window.
  4. R4 kind() returns "window", "Swing control", "AWT component" (a Component that is neither a window nor a Swing control) or "not a component".
  5. R5 Running the test program prints exactly what it expects. (verified by the program output)

Before you code: warm-up and model answers

  1. Trace ancestry() for new JButton("Print map"). What does it return, and what does that chain tell you about whether a JButton is a Container?

    JButton < AbstractButton < JComponent < Container < Component < Object. Container is an ancestor, so every JButton is a Container.

  2. The starter says Jukebox and JFrame are both Swing controls. Which sentence in section 14.1 gives a test that doesn't depend on names?

    Each Swing component is a descendant of JComponent, so the test is whether the object is a JComponent (instanceof JComponent). JFrame and Jukebox are not.

Solution

ComponentAudit.java
import javax.swing.*;
import java.awt.*;

public class ComponentAudit
{
    // Returns the object's class and every ancestor class, for example
    // "JLabel < JComponent < Container < Component < Object".
    public static String ancestry(Object item)
    {
        String chain = item.getClass().getSimpleName();
        Class<?> parent = item.getClass().getSuperclass();
        while (parent != null)
        {
            chain += " < " + parent.getSimpleName();
            parent = parent.getSuperclass();
        }
        return chain;
    }

    // True for the Swing controls you place in a window: labels, buttons, text fields...
    public static boolean isSwingControl(Object item)
    {
        return item instanceof JComponent;
    }

    // True for anything that can hold other components.
    public static boolean isContainer(Object item)
    {
        return item instanceof Container;
    }

    // True for a top-level window such as a JFrame.
    public static boolean isWindow(Object item)
    {
        return item instanceof Window;
    }

    // "window", "Swing control", "AWT component" or "not a component"
    public static String kind(Object item)
    {
        if (isWindow(item))
            return "window";
        if (isSwingControl(item))
            return "Swing control";
        if (item instanceof Component)
            return "AWT component";
        return "not a component";
    }
}

Walkthrough

Section 14.1 (p. 546) says each Swing component descends from JComponent, which inherits from java.awt.Container, so instanceof JComponent identifies the controls and instanceof Container identifies anything that can hold components. That is why a JButton reports container: true: through JComponent it is a Container. Figure 14-1 (p. 547) shows JFrame descending from Frame, Window, Container and Component; JComponent is not on that chain, so a frame is a window but not a Swing control. In kind() the order matters only for the last test: a JButton is also a Component, so instanceof Component must come after the more specific questions. ButtonGroup is in javax.swing yet descends directly from Object (p. 574), and Jukebox merely starts with J; neither is a component. Names starting with J are a reading aid for people (p. 546), not something a program should rely on.

TestComponentAudit.java
import javax.swing.*;
import java.awt.*;

public class TestComponentAudit
{
    // The kiosk's music player. It is not part of the GUI.
    static class Jukebox
    {
    }

    public static void main(String[] args)
    {
        Object[] items = { new JLabel("Welcome"), new JButton("Print map"),
            new JFrame("Kiosk"), new Button("Old print button"),
            new ButtonGroup(), new Jukebox() };
        for (Object item : items)
        {
            System.out.println(ComponentAudit.ancestry(item));
            System.out.println("  control: " + ComponentAudit.isSwingControl(item)

                + " -> " + ComponentAudit.kind(item));

        System.exit(0);   // close the window objects this test created
    }
}

Messages students see when a check fails

C1 · Controls are found by type, not by name

Return item instanceof JComponent;. Every Swing control descends from JComponent, whatever its name; a class called Jukebox is not one.

C2 · Any Container can hold components

Return item instanceof Container;. Frames are containers, but so is every JComponent, because JComponent inherits from java.awt.Container.

C3 · Windows are found with instanceof Window

Return item instanceof Window;. Figure 14-1 shows JFrame descending from Frame, which descends from Window.

C4 · kind() recognises plain AWT components

After the window and Swing-control questions, return "AWT component" when item instanceof Component. An AWT Button is a Component but not a JComponent.

Progressive hints

  1. instanceof asks whether an object is a member of a class or of any class that descends from it. Pick the class for each question from the ancestry lines the program prints.

  2. Look at the ancestry of JFrame: JComponent isn't on it, but Container and Window are.

  3. In kind(), ask the specific questions first. Every Swing control is also a Component, so the Component test must come last.

Reflection: questions and model answers

  1. Your audit says a JButton is a container. Use its ancestry line to explain why that is true, and why it still doesn't make a button the place to put other components.

    JButton descends from JComponent, which descends from Container, so every button is a Container and inherits add(). Being able to doesn't mean it's designed for it: a button is a control the user clicks, and frames are the containers meant to hold controls.

  2. Why is checking whether a class name starts with J a fragile way for a program to decide what an object is? Use two objects from this lab as examples.

    Names are conventions people choose. Jukebox starts with J but isn't a GUI component, and JFrame starts with J but isn't a JComponent. instanceof asks the type system, which a name can't fool.
