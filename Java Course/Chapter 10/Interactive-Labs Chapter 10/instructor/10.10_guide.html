The check-in kiosk that wouldn't compile on a Mac

Objectives

  • Call a method written by others that throws a checked IOException
  • Decide between catching the exception and adding throws IOException to a header
  • Keep a program running, at a reduced level, when an optional tool can't start

Requirements

  1. R1 The exec() call is in a try block, followed by catch (IOException ...) that prints Could not start <command[0]> and returns false.
  2. R2 openTool() returns true when exec() succeeds, and its header has no throws clause.
  3. R3 Running the test program prints exactly what it expects. (verified by the program output)

Before you code: warm-up and model answers

  1. The starter's only new statement is the call to exec(). Why does that one statement stop the whole file from compiling, when nextLine() in the kiosk compiles without any try block?

    exec() declares a checked IOException, so the compiler requires openTool() to catch it or declare it. nextLine() can only throw unchecked exceptions, which don't need to be caught or declared.

  2. If openTool() declared throws IOException (and so did main()), what would happen on a kiosk where the keyboard program can't start?

    The IOException would travel up to main() and out to the JVM, and the program would end with a stack trace before asking for the patient's name. Check-in would stop.

Solution

KeyboardLauncher.java
import java.io.IOException;

public class KeyboardLauncher
{
    // Starts a helper program, such as the Windows on-screen keyboard.
    // command[0] is the program; any other elements are its arguments.
    // Returns true if the program started.
    public static boolean openTool(String[] command)
    {
        try
        {
            Process proc = Runtime.getRuntime().exec(command);
            return true;
        }
        catch (IOException e)
        {
            System.out.println("Could not start " + command[0]);
            return false;
        }
    }
}

Walkthrough

exec() declares throws IOException, a checked exception, so a method that calls it must catch it or specify it (p. 430; section 10.6). Specifying it all the way up to main(), the alternative in the note on p. 431, would end the program when the keyboard can't start, so the kiosk catches it in openTool() and continues without the on-screen keyboard: the program stays fault tolerant (p. 396). The book's Figure 10-48 passes one String, exec("cmd /c ..."); this lab uses the String[] form because exec(String) has been deprecated since JDK 18, so newer compilers warn about it. On Windows, CheckInKiosk really opens the keyboard. Running a command that doesn't exist is the reliable way to make exec() throw on every operating system, which is why the test program asks for no-such-keyboard-app. The unused proc variable mirrors Figure 10-48; Runtime.getRuntime().exec(command); alone is fine too.

Messages students see when a check fails

C1 · exec() is tried and the IOException caught

Put the exec() call in a try block and follow it with catch (IOException e). That handles the failure here, so the kiosk can carry on without the on-screen keyboard.

C2 · The catch block reports and returns false

In the catch block, print "Could not start " + command[0] and return false;, so the caller knows to show the tip.

C3 · Success returns true and nothing is passed on

Keep the header as public static boolean openTool(String[] command), with no throws clause. The clinic wants the kiosk to survive a missing keyboard, so this method handles the exception.

Progressive hints

  1. Read the compiler message: it gives you the two choices from section 10.6. The brief tells you which one the clinic wants.

  2. Two outcomes, two return values: one at the end of the try block, one in the catch block.

  3. The program name is the first element of the array the caller passed in.

Reflection: questions and model answers

  1. The note on p. 431 says many programmers would simply add throws IOException to main(). When is that reasonable, and why wasn't it here?

    It is reasonable in a small demo where failing to open the keyboard can just end the program. Here the keyboard is optional and check-in is essential, so the failure must be handled where it happens and the program must continue.

  2. Fault-tolerant programs keep working “possibly at a reduced level” when something fails (p. 396). What is the reduced level for this kiosk?

    Patients can still check in, but only with the physical keyboard: the on-screen keyboard isn't available, and the kiosk shows a tip instead of crashing.
