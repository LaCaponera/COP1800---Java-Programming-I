The thermostat log that gave up after one typo

Objectives

  • Place a statement that might fail in a try block and handle the failure in a catch block
  • Use the catch block to repair the data so the program continues with a valid value
  • Clear the rest of a bad input line with nextLine() so later entries can still be read

Requirements

  1. R1 The call to nextInt() is inside a try block, and a catch block that catches InputMismatchException (or Exception) prints Reading N skipped: not a whole number.
  2. R2 The catch block stores a usable value in temps[x]: the previous reading, or SET_POINT when the first reading is bad.
  3. R3 After each reading, good or bad, nextLine() discards the rest of the line.
  4. R4 Running the test program prints exactly what it expects. (verified by the program output)

Before you code: warm-up and model answers

  1. Suppose you put nextInt() in a try block and a catch block that only prints the message, but no nextLine(). The log is 68, 71, seventy, 72, ... Predict which readings get skipped, and why.

    Readings 3, 4, 5 and 6 are all skipped. nextInt() leaves the word seventy in the input when it fails, so every later nextInt() call meets the same word and fails again (Figure 10-13).

  2. A classmate writes int t = input.nextInt(); inside the try block and temps[x] = t; after the catch block. What does the compiler say, and why?

    cannot find symbol t. A variable declared inside a try block is local to that block, so it is out of scope after the block ends (p. 402).

Solution

ReadingLog.java
import java.util.InputMismatchException;
import java.util.Scanner;

public class ReadingLog
{
    public static final int SET_POINT = 70;

    // Reads `count` temperatures, one per line, and returns them.
    public static int[] readTemperatures(Scanner input, int count)
    {
        int[] temps = new int[count];
        for (int x = 0; x < count; ++x)
        {
            try
            {
                temps[x] = input.nextInt();
            }
            catch (InputMismatchException e)
            {
                System.out.println("Reading " + (x + 1) + " skipped: not a whole number");
                if (x == 0)
                    temps[x] = SET_POINT;
                else
                    temps[x] = temps[x - 1];
            }
            input.nextLine();
        }
        return temps;
    }

    public static double average(int[] temps)
    {
        int total = 0;
        for (int x = 0; x < temps.length; ++x)
            total += temps[x];
        return (double) total / temps.length;
    }
}

Walkthrough

nextInt() throws an InputMismatchException when the next token isn't an int, so it goes in the try block and the catch block reports the problem (pp. 397–399). The catch block also repairs the data, the idea in Figure 10-11 (p. 400): after the try...catch pair, temps[x] is guaranteed to hold a usable value. When nextInt() fails, the Scanner does not consume the bad token, so without nextLine() every later call fails on the same word (Figures 10-12 to 10-14, p. 401). Calling nextLine() after the try...catch pair, not only in the catch block, also clears 70 F: nextInt() succeeds on 70, but the F is still on the line. catch (Exception e) passes too (the book uses it in Figure 10-12); the specific type documents what you expect and needs import java.util.InputMismatchException; or java.util.*.

Test program

TestReadingLog.java
import java.util.Locale;
import java.util.Scanner;

public class TestReadingLog
{
    public static void main(String[] args)
    {
        Scanner lobby = new Scanner("68\n71\nseventy\n72\n70 F\n69\n");
        show("Lobby", ReadingLog.readTemperatures(lobby, 6));

        Scanner gym = new Scanner("cold\n66\n");
        show("Gym", ReadingLog.readTemperatures(gym, 2));
    }

    private static void show(String room, int[] temps)
    {
        System.out.print(room + ":");
        for (int t : temps)
            System.out.print(" " + t);
        System.out.println();
        System.out.println(room + " average: "
            + String.format(Locale.US, "%.1f", ReadingLog.average(temps)));
    }
}

Messages students see when a check fails

C1 · nextInt() is tried

Put the nextInt() call inside a try { ... } block. It is the statement that throws when the line holds a word.

C2 · A catch block handles the bad entry

Follow the try block with catch (InputMismatchException e) (or catch (Exception e)). Without a matching catch block the exception still ends the program.

Hint:

InputMismatchException is in java.util, like Scanner: import it, or import java.util.*.

C3 · The catch block stores a usable reading

In the catch block, assign temps[x]: the previous reading, or SET_POINT when x is 0. Otherwise the slot keeps 0 and drags the average down.

C4 · The rest of the line is discarded

Call input.nextLine() after each reading to throw away what is left of the line. When nextInt() fails, the bad word stays in the input until something reads it.

Progressive hints

  1. Wrap only the risky statement: the one that converts the typed text into an int.

  2. In the catch block you know x, so you know which reading failed and whether there is a previous one to copy.

  3. Look at the line 70 F: nextInt() succeeds there, yet something is left behind. Where must the line-clearing call go so it runs after a good reading too?

Reflection: questions and model answers

  1. Why is copying the previous reading better for this report than leaving 0 in the array after a bad line?

    A 0 is a real-looking temperature that pulls the average far down (the lobby would average about 58 instead of 70). Repeating the previous reading keeps the average close to reality, and the printed message still tells staff that a value was estimated.

  2. When nextInt() fails on seventy, which statements of the try block run, and which statement runs next?

    The try block is abandoned at the failing nextInt() call, so the assignment to temps[x] never happens. Control jumps to the matching catch block, and after it the statement following the try...catch pair (nextLine()) runs.

Extension

Readings above 110 or below 32 are almost certainly typos too, but nextInt() accepts them. Should those be handled with an exception or with a decision? Add the check you choose and print Reading N skipped: out of range.
