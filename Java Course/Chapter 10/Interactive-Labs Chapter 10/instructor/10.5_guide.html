The group order that reported the wrong mistake

Objectives

  • Rewrite nested error-checking if statements as one try block followed by catch blocks
  • Explain how grouping the normal steps together makes logic easier to follow and harder to get wrong
  • Use methods that throw exceptions without handling them, and decide how the caller responds

Requirements

  1. R1 summary() calls priceOf(), parseQuantity() and shareOf() in one try block, together with the line that builds the total, and no longer uses the pre-checks (isItemCode(), isWholeNumber(), people != 0).
  2. R2 Catch blocks return Error: unknown item code for ArrayIndexOutOfBoundsException, Error: quantity must be a whole number for NumberFormatException, and Error: party size can't be 0 for ArithmeticException.
  3. R3 Running the test program prints exactly what it expects. (verified by the program output)

Before you code: warm-up and model answers

  1. Trace the starter for summary(5, "2", 2). Which test fails first, which else runs, and what message does the customer see?

    isItemCode(5) is false, so the outermost else runs and returns Error: quantity must be a whole number, although the real problem is the item code. That else holds the wrong message.

  2. In the rewrite, summary(9, "two", 0) has three problems. Which message will it show, and why only that one?

    Error: unknown item code. priceOf(9) is the first statement to throw; the rest of the try block is abandoned, so the quantity and party size are never examined.

Starter files

Store.java (read-only for students)
public class Store
{
    private static final int[] PRICES = {450, 1299, 2500};   // cents, by item code

    // Throws ArrayIndexOutOfBoundsException for an unknown item code.
    public static int priceOf(int itemCode)
    {
        return PRICES[itemCode];
    }

    // Throws NumberFormatException when the text isn't a whole number.
    public static int parseQuantity(String text)
    {
        return Integer.parseInt(text);
    }

    // Throws ArithmeticException when people is 0.
    public static int shareOf(int totalCents, int people)
    {
        return totalCents / people;
    }

    // Pre-checks used by the old order screen.
    public static boolean isItemCode(int itemCode)
    {
        return itemCode >= 0 && itemCode < PRICES.length;
    }

    public static boolean isWholeNumber(String text)
    {
        if (text.length() == 0)
            return false;
        for (int x = 0; x < text.length(); ++x)
            if (!Character.isDigit(text.charAt(x)))
                return false;
        return true;
    }

    // 3897 -> "$38.97"
    public static String money(int cents)
    {
        String pennies = "" + cents % 100;
        if (cents % 100 < 10)
            pennies = "0" + pennies;
        return "$" + cents / 100 + "." + pennies;
    }
}

public class OrderDesk
{
    // One line for the group-order screen: the total and each share, or an error.
    public static String summary(int itemCode, String qtyText, int people)
    {
        // TODO (R1, R2): rewrite with one try block and three catch blocks.
        // The normal steps are buried, and two messages are on the wrong branches.
        String result;
        if (Store.isItemCode(itemCode))
        {
            int price = Store.priceOf(itemCode);
            if (Store.isWholeNumber(qtyText))
            {

                if (people != 0)
                {
                    int share = Store.shareOf(total, people);
                    result = "Total " + Store.money(total) + ", " + Store.money(share) + " each";
                }
                else
                    result = "Error: party size can't be 0";
            }
            else
                result = "Error: unknown item code";
        }
        else
            result = "Error: quantity must be a whole number";
        return result;
    }
}

Solution

OrderDesk.java
public class OrderDesk
{
    // One line for the group-order screen: the total and each share, or an error.
    public static String summary(int itemCode, String qtyText, int people)
    {
        String result;
        try
        {
            int price = Store.priceOf(itemCode);
            int total = price * Store.parseQuantity(qtyText);
            int share = Store.shareOf(total, people);
            result = "Total " + Store.money(total) + ", " + Store.money(share) + " each";
        }
        catch (ArrayIndexOutOfBoundsException e)
        {
            result = "Error: unknown item code";
        }
        catch (NumberFormatException e)
        {
            result = "Error: quantity must be a whole number";
        }
        catch (ArithmeticException e)
        {
            result = "Error: party size can't be 0";
        }
        return result;
    }
}

Walkthrough

This is Figure 10-26 versus Figure 10-27 (pp. 410–411). In the nested version the purpose of the method, building the summary, is lost in a maze of if statements, and the starter shows the risk the book names: with three levels of nesting, two else branches carry each other's messages. In the try version the business-as-usual steps read top to bottom, and each problem is handled in its own catch block. The methods in Store detect the errors but don't handle them; the caller decides what to do, which is the flexibility the book describes on p. 411. Because the try block is abandoned at the first failure, the steps still happen in the right order: (9, "two", 0) reports the unknown item. IndexOutOfBoundsException (the parent class) is accepted for the first catch block.

Messages students see when a check fails

C1 · The normal steps are together in one try block

Put the three Store calls in a single try { ... } block, in order, together with the statement that builds the summary. The normal path should read top to bottom without nesting.

C2 · The old pre-checks are gone

Delete the isItemCode(), isWholeNumber() and people != 0 tests. The Store methods already detect those problems and throw; your catch blocks handle them.

C3 · One catch block per problem

Add three catch blocks after the try block: ArrayIndexOutOfBoundsException (unknown item code), NumberFormatException (quantity) and ArithmeticException (party size), each setting its own message. The comments in Store.java say which method throws which.

Progressive hints

  1. Ignore the error handling for a moment. Write the four normal steps one after another, with no if at all.

  2. Now wrap those steps in a try block. Store.java's comments list the three exception types you can expect.

  3. Each catch block sets result to one message. Check each message against the cause it describes; that mix-up was the original bug.

Reflection: questions and model answers

  1. Compare the two versions of summary(). Why was the message mix-up easy to make in the nested version and hard to make in yours?

    In the nested version each else is far from the test it belongs to, so it is easy to attach a message to the wrong branch. In the try version each catch block names the exception type right next to its message, so cause and message sit together.

  2. Store throws but never catches. Describe a different program (a kiosk, a phone app, a nightly report) that should respond to one of these exceptions differently, and how.

    Example: a nightly sales report could skip an order with an unknown item code and log it instead of showing an error line to a customer. Because Store only throws, each caller chooses its own response (p. 411).
