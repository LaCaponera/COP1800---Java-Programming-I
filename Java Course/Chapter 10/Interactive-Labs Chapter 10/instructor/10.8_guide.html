COP1800 · Java Programming I · Lab 10.8

The climbing class that said “Class full” to nobody

Objectives

  • Create an Exception subclass whose constructor passes a message to super()
  • Throw your exception from a method and declare it in that method's header
  • Catch your exception in the caller and respond to it with getMessage()

Requirements

  1. R1 ClassFullException extends Exception. Its constructor takes a String class name and passes <name> is full to super().
  2. R2 enroll() declares throws ClassFullException and throws a new ClassFullException when the roster is full, instead of printing.
  3. R3 FrontDesk.signUp() catches the ClassFullException, adds the member to the waitlist, and prints <message>; <member> is #N on the waitlist.
  4. R4 Running the test program prints exactly what it expects. (verified by the program output)

Before you code: warm-up and model answers

  1. With the starter, what does the front desk print when Priya signs up for a full class? Why is that worse than a crash?

    Class full, then Priya is in Bouldering 101. enroll() returns normally, so signUp() can't tell anything went wrong and confirms a place Priya doesn't have. A crash would at least be noticed.

  2. Why should ClassFullException extend Exception rather than Error, and what does that choice force on every caller of enroll()?

    Error is for serious problems a program can't recover from; a full class is recoverable (waitlist, another session). Extending Exception (not RuntimeException) makes it checked, so every caller must catch it or declare it.

Solution

ClassFullException.java
public class ClassFullException extends Exception
{
    public ClassFullException(String className)
    {
        super(className + " is full");
    }
}
ClimbingClass.java
public class ClimbingClass
{
    private String name;
    private String[] roster;
    private int count;

    public ClimbingClass(String className, int places)
    {
        name = className;
        roster = new String[places];
    }

    public String getName()
    {
        return name;
    }

    public int getCount()
    {
        return count;
    }

    public void enroll(String member) throws ClassFullException
    {
        if (count == roster.length)
            throw new ClassFullException(name);
        roster[count] = member;
        ++count;
    }
}
FrontDesk.java
public class FrontDesk
{
    private String[] waitlist = new String[10];
    private int waiting;

    // Signs a member up. When the class is full, the member goes on the waitlist.
    public void signUp(ClimbingClass session, String member)
    {
        try
        {
            session.enroll(member);
            System.out.println(member + " is in " + session.getName());
        }
        catch (ClassFullException e)
        {
            waitlist[waiting] = member;
            ++waiting;
            System.out.println(e.getMessage() + "; " + member + " is #" + waiting
                + " on the waitlist");
        }
    }

    public int getWaiting()
    {
        return waiting;
    }
}

Walkthrough

To be throwable, a class must extend a subclass of Throwable; for recoverable situations it extends Exception, and by convention its name ends in Exception (p. 419). Passing the text to super(message) uses the Exception(String message) constructor, so getMessage() returns it later (p. 419, Figure 10-37). Because ClassFullException extends Exception and not RuntimeException, it is checked: enroll() must declare it, and every caller must catch or declare it (section 10.6). throw new ClassFullException(name) creates the object only when it is needed, as in Figure 10-38 (pp. 419–420). The front desk and the app react differently to the same exception, which is the point of throwing it rather than printing (p. 421). Keep the success message inside the try block: if enroll() throws, it must not print that the member is in.

Messages students see when a check fails

C1 · ClassFullException is a checked exception

Write the header as public class ClassFullException extends Exception. Extending Exception (not RuntimeException) makes it a checked exception, so callers can't ignore it.

C2 · The constructor passes the message to super()

Give the class a constructor public ClassFullException(String className) whose first statement is super(className + " is full");. The parent stores the text, and getMessage() returns it.

Hint:

Figure 10-37 (p. 419) passes a fixed String to super(); yours builds it from the parameter.

C3 · enroll() declares the exception

Add throws ClassFullException to the end of the enroll() header. It is a checked exception, so a method that throws it without catching it must say so.

C4 · enroll() throws instead of printing

Replace the print and the return with throw new ClassFullException(name);. Throwing hands the problem to the caller, and the caller decides what to say.

C5 · The front desk catches the exception

Put session.enroll(member); and the success message in a try block, followed by catch (ClassFullException e). In the catch block, add the member to waitlist and print the message.

C6 · The waitlist message uses getMessage()

Start the waitlist line with e.getMessage(), so the wording lives in one place: the exception class.

Progressive hints

  1. Start with ClassFullException.java: compare it with HighBalanceException in Figure 10-37 (p. 419). What changes when the message depends on the class name?

  2. In enroll(), the if stays; only what happens inside it changes. Remember the header, too: the compiler checks it.

  3. In signUp(), the line that says the member is in must only run if enroll() succeeded. Which block guarantees that?

Reflection: questions and model answers

  1. The front desk and the app handle the full class differently. Why is that only possible because enroll() throws instead of printing?

    Printing decides the response inside enroll(), once for everyone, and the caller never learns about it. Throwing reports the problem to whoever called, so each caller can choose: the desk uses the waitlist, the app suggests tomorrow's sessions.

  2. The book warns against creating too many Exception types (p. 421). Was a new class justified here, or would a built-in exception have done? Explain.

    Justified: no built-in exception means “class full”, and catching something general like IllegalStateException could also catch unrelated bugs. A named type documents the situation and lets callers catch exactly it. (A well-argued no is acceptable too.)

Extension

Add ClassCancelledException for a session the gym cancels, thrown by enroll() when a cancelled flag is true. Should the front desk handle it in the same catch block or a separate one? Write the catch block(s) and a test line.
