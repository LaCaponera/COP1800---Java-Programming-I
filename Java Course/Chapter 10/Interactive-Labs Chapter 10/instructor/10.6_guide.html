COP1800 · Java Programming I · Lab 10.6

The greenhouse dashboard that won't compile

Objectives

  • Tell checked exceptions from unchecked ones and apply the catch-or-specify requirement
  • Declare an exception with a throws clause when the caller should decide what to do
  • Choose, method by method, whether to catch an exception or pass it on

Requirements

  1. R1 statusLine() catches the IOException and returns Bed N: sensor offline. Its header has no throws clause.
  2. R2 averageTemperature() declares throws IOException in its header and does not catch the exception.
  3. R3 Greenhouse.java imports java.io.IOException.
  4. R4 Running the test program prints exactly what it expects. (verified by the program output)

Before you code: warm-up and model answers

  1. READINGS[bed - 1] could also throw an exception, yet the compiler only complains about readTemperature(). What is the difference between the two exceptions?

    ArrayIndexOutOfBoundsException is unchecked (it descends from RuntimeException), so Java doesn't require catching or declaring it. IOException is checked, so every method that can receive it must catch it or specify it in a throws clause (pp. 413–414).

  2. Both methods read the same sensor. Why should one catch the exception and the other pass it on?

    The dashboard can recover by showing “sensor offline” for one bed. averageTemperature() can't produce a true average without bed 3, and the controller is the one that knows what to do with the vents, so the decision belongs to it.

Starter files

GreenhouseSensor.java (read-only for students)
import java.io.IOException;

public class GreenhouseSensor
{
    private static final double[] READINGS = {21.5, 23.0, 0.0, 22.5};

    // Reads the wireless sensor in a bed (1 to 4).
    // Today the sensor in bed 3 is offline.
    public static double readTemperature(int bed) throws IOException
    {
        if (bed == 3)
            throw new IOException("Sensor " + bed + " is offline");
        return READINGS[bed - 1];
    }
}
Greenhouse.java
public class Greenhouse
{
    // Dashboard: one line per bed. A dead sensor must not stop the dashboard.
    public static String statusLine(int bed)
    {
        // TODO (R1): readTemperature() can throw a checked IOException.
        return "Bed " + bed + ": " + GreenhouseSensor.readTemperature(bed) + " C";
    }

    // Climate controller: the average of the given beds.
    // The controller must know when a reading failed, so don't hide it here.
    public static double averageTemperature(int[] beds)
    {
        // TODO (R2): pass the IOException on to the caller.
        double total = 0;
        for (int x = 0; x < beds.length; ++x)
            total += GreenhouseSensor.readTemperature(beds[x]);
        return total / beds.length;
    }
}

Solution

Greenhouse.java
import java.io.IOException;

public class Greenhouse
{
    // Dashboard: one line per bed. A dead sensor must not stop the dashboard.
    public static String statusLine(int bed)
    {
        try
        {
            return "Bed " + bed + ": " + GreenhouseSensor.readTemperature(bed) + " C";
        }
        catch (IOException e)
        {
            return "Bed " + bed + ": sensor offline";
        }
    }

    // Climate controller: the average of the given beds.
    // The controller must know when a reading failed, so don't hide it here.
    public static double averageTemperature(int[] beds) throws IOException
    {
        double total = 0;
        for (int x = 0; x < beds.length; ++x)
            total += GreenhouseSensor.readTemperature(beds[x]);
        return total / beds.length;
    }
}

Walkthrough

IOException descends from Exception but not from RuntimeException, so it is a checked exception and subject to the catch or specify requirement: a method that can receive it must catch it or list it in a throws clause, or the code won't compile (pp. 413–414). Both choices are legitimate, and this lab needs one of each. The dashboard can recover, so statusLine() catches. The average has no honest value when a sensor is missing, so averageTemperature() specifies the exception and the controller, like the two PriceList applications (pp. 412–413), decides for itself. The test program's catch (IOException e) only compiles because the header says the method can throw it; if a student catches inside averageTemperature() instead, javac reports that the exception is never thrown in the body of the try. READINGS[bed - 1] could throw an ArrayIndexOutOfBoundsException, but that is unchecked, so nothing has to be declared for it.

Test program

Students run it in an IDE and paste the output into the page.

TestGreenhouse.java
import java.io.IOException;

public class TestGreenhouse
{
    public static void main(String[] args)
    {
        for (int bed = 1; bed <= 4; ++bed)
            System.out.println(Greenhouse.statusLine(bed));

        int[] east = {1, 2};
        int[] all = {1, 2, 3, 4};
        try
        {
            System.out.println("East average: "
                + Greenhouse.averageTemperature(east) + " C");
            System.out.println("Full average: "
                + Greenhouse.averageTemperature(all) + " C");
        }
        catch (IOException e)
        {
            System.out.println("Controller: " + e.getMessage() + "; vents unchanged");
        }
    }
}

Messages students see when a check fails

C1 · statusLine() catches the IOException

Call readTemperature() inside a try block and follow it with catch (IOException e) that returns "Bed " + bed + ": sensor offline". The dashboard can recover, so it handles the problem itself.

C2 · statusLine() doesn't pass the problem on

Remove the throws clause from statusLine(). Once it catches the exception, nothing is left to declare, and the dashboard shouldn't have to deal with it.

C3 · averageTemperature() specifies the IOException

End the header with throws IOException: public static double averageTemperature(int[] beds) throws IOException. That tells every caller it must catch or pass on the failure.

Hint:

Be specific: throws Exception would compile here but hides which failure to expect (p. 415).

C4 · averageTemperature() doesn't hide the failure

Don't catch the exception in averageTemperature(). Any average it returned would be made up; let the controller decide.

C5 · IOException is imported

Add import java.io.IOException; at the top. Unlike ArithmeticException, IOException is in the java.io package, which isn't imported automatically.

Progressive hints

  1. The compiler message offers exactly two choices: “caught” or “declared to be thrown”. Pick one for each method using the brief.

  2. For the dashboard, a try block around the reading and a catch block that returns a different line is enough.

  3. For the controller, the change is in the method header, not in its body. Look at how readTemperature() announces its exception.

Reflection: questions and model answers

  1. Some programmers call checked exceptions “syntactic salt” (p. 414). Using this lab, explain what the salt protected you from.

    The compiler refused to build until each caller of readTemperature() made a decision. Without that rule, the dashboard and controller could have ignored the offline sensor until it crashed in the greenhouse; the salt forced the failure to be planned for.

  2. Why is throws IOException better than throws Exception in the header of averageTemperature()?

    IOException tells callers exactly which failure to expect and lets them catch just that. throws Exception hides the information and forces callers to deal with every possible exception (p. 415).
