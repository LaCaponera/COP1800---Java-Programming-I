COP1800 · Java Programming I · Lab 10.1

The driver dashboard that crashed on a day off

Objectives

  • Read an exception message and its stack trace: the type, the method, the file and the line
  • Tell an Exception (a program can recover) from an Error (it usually can't)
  • Prevent a runtime exception with a decision, the traditional technique on pp. 396–397

Requirements

  1. R1 averageFareCents() returns 0 when trips is 0. Test trips before you divide.
  2. R2 averageSpeed() returns 0.0 when hours is 0, instead of Infinity or NaN.
  3. R3 Running the test program prints exactly what it expects. (verified by the program output)

Before you code: warm-up and model answers

  1. Read the support log in the brief. What type of exception is it, in which method and on which line of which file was it thrown, and which line of the test program made that call?

    An ArithmeticException with the message / by zero, thrown in DriverStats.averageFareCents at line 7 of DriverStats.java. It was called from line 10 of TestDriverStats.java, in main().

  2. With the starter, predict averageSpeed(0.0, 0.0) and averageSpeed(12.5, 0.0). Will either one crash?

    Neither crashes. Dividing a double by 0 is allowed: 12.5 / 0.0 is Infinity and 0.0 / 0.0 is NaN (not a number).

Solution

DriverStats.java
public class DriverStats
{
    // Average fare per trip, in cents (integer division).
    public static int averageFareCents(int totalCents, int trips)
    {
        if (trips == 0)
            return 0;
        return totalCents / trips;
    }

    // Average speed in miles per hour.
    public static double averageSpeed(double miles, double hours)
    {
        if (hours <= 0)
            return 0.0;
        return miles / hours;
    }
}

Walkthrough

Integer division by 0 has no answer, so Java throws an ArithmeticException with the message / by zero (p. 395). The trace says where: DriverStats.averageFareCents, line 7 of DriverStats.java, called from line 10 of the test program. It is an Exception, not an Error, so the program can recover (p. 394); here the simplest recovery is to never divide, using a decision as Division2 does (Figure 10-5, p. 397). Floating-point division by 0 is allowed and gives Infinity (p. 395), and 0.0 / 0.0 gives NaN, so the speed method throws nothing and a catch block would never run: only a decision can catch that mistake. hours <= 0 also rejects a negative time from a bad clock; hours == 0 passes the test as well.

Messages students see when a check fails

C1 · averageFareCents() tests trips before dividing

Before totalCents / trips, test whether trips is 0 and return 0 in that case. The trace shows the crash comes from exactly that division.

Hint:

Figure 10-5 (p. 397) prevents the same crash with one if.

C2 · averageSpeed() tests hours before dividing

Test hours before dividing and return 0.0 when it is 0. A double divided by 0 gives Infinity or NaN instead of throwing, so only a decision notices the problem.

C3 · No catch block waiting for a crash that never comes

Remove the catch from averageSpeed(). Dividing a double by 0 never throws, so the catch block can't run; the decision is what protects this method.

Progressive hints

  1. Start with the trace: the top at line names the method and line that divided by 0. What should a driver with zero trips see there?

  2. Division2 on p. 397 asks one question before it divides. Ask the same question about trips and return 0 early.

  3. Doubles behave differently: p. 395 says dividing a double by 0 is allowed. The speed method needs its own test of hours, because nothing will be thrown.

Reflection: questions and model answers

  1. The fare method crashed, but the speed method quietly returned Infinity. Which failure is more dangerous for a driver dashboard, and why?

    The quiet one. The crash is noticed and reported at once, with a trace that points to the line. Infinity or NaN flows into charts and weekly reports with no warning, so nobody knows the numbers are wrong.

  2. The trace had two at lines. What does the top one tell you, and what does the bottom one add?

    The top line is where the exception was thrown (the division in averageFareCents, line 7). The bottom line is the call that passed 0 trips (main in the test program), which tells you which caller supplied the data that caused it.

Extension

Add fuelEconomy(double miles, double gallons) and decide what it should return for 0 gallons. Then think ahead: Division2's if can't help when a user types six instead of 6, because nextInt() throws before your code gets the value. Section 10.2 handles that case.
