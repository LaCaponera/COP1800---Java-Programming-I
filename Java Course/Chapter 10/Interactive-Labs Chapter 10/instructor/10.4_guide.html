The laser cutter that stayed locked all afternoon

Objectives

  • Use a finally block for cleanup that must happen whether or not an exception occurs
  • Explain why code after a try...catch pair might never run
  • Replace repeated cleanup code with a single finally block

Requirements

  1. R1 runJob() calls unlock() exactly once, in a finally block after the try...catch pair.
  2. R2 runJob() still catches only ArithmeticException. The bad material code reaches the front desk.
  3. R3 Running the test program prints exactly what it expects. (verified by the program output)

Before you code: warm-up and model answers

  1. With the starter, follow Chi's job (material code 7). Which statement throws, which of the two unlock() calls runs, and what happens to Dev's job?

    MATERIALS[7] throws an ArrayIndexOutOfBoundsException. There is no matching catch block, so neither unlock() runs and the method is abandoned. The cutter stays locked, so Dev is refused.

  2. If the cutter were unlocked in a statement written after the catch block (no finally), would Chi's job unlock it? Why or why not?

    No. An uncaught exception abandons the method immediately, so statements after the try...catch pair never run (p. 409). Only a finally block is guaranteed to run.

Solution

LaserCutter.java
public class LaserCutter
{
    private static final String[] MATERIALS = {"acrylic", "plywood", "cardboard"};
    private boolean locked = false;

    public boolean isLocked()
    {
        return locked;
    }

    private void unlock()
    {
        locked = false;
        System.out.println("  cutter unlocked");
    }

    public void runJob(String member, int materialCode, int minutes, int sheets)
    {
        if (locked)
        {
            System.out.println(member + " refused: cutter is locked");
            return;
        }
        locked = true;
        System.out.println(member + " locks the cutter");
        try
        {
            String material = MATERIALS[materialCode];
            int perSheet = minutes / sheets;
            System.out.println("  " + sheets + " sheets of " + material + ", "
                + perSheet + " min each");
        }
        catch (ArithmeticException e)
        {
            System.out.println("  no sheets loaded");
        }
        finally
        {
            unlock();
        }
    }
}

Walkthrough

Statements after a try...catch pair don't always run: an exception with no matching catch block abandons the method at once (p. 409). The finally block runs on all three paths the book lists: the try ends normally, the catch executes, or an uncaught exception leaves the method early (p. 409). That is why Chi's output shows cutter unlocked before the front desk's message: the finally block runs on the way out, then the exception continues to the caller. One unlock() in finally also replaces the two copies, which the book calls clearer and less prone to error (p. 410). The return for a locked cutter comes before the try block, so that path correctly unlocks nothing.

Messages students see when a check fails

C1 · unlock() is called in a finally block

Add finally { unlock(); } after the catch block. A finally block runs whether the job worked, was caught, or threw something this method doesn't catch.

C2 · unlock() appears only once

Delete the unlock() calls from the try and catch blocks. With the finally block they would unlock twice and print cutter unlocked twice.

C3 · The bad material code still reaches the front desk

Keep catch (ArithmeticException e) and don't catch the bad material code here. The front desk decides what to tell Chi; finally already makes sure the cutter is unlocked.

Progressive hints

  1. Count the paths out of runJob() after the cutter is locked: normal, caught, and uncaught. Which of them reach an unlock() call?

  2. Figure 10-24 (p. 408) shows where the third kind of block goes: right after the last catch block.

  3. Once the cleanup lives in that block, the copies in the try and catch blocks are extra. Keep one.

Reflection: questions and model answers

  1. Explain the order of the two lines printed for Chi's job: why does the finally block run before the front desk's catch block?

    The exception leaves runJob() without a matching catch there. Before the method is abandoned, its finally block runs and unlocks the cutter; only then does the exception travel back to main, where the front desk's catch block runs.

  2. Name another real situation where cleanup must happen no matter how a task ends, and say what would go wrong without a finally block.

    Example: closing a data file after reading it (p. 409). Without finally, an unexpected exception leaves the file open, so other programs can't use it or data isn't saved. Any answer with a resource that must be released fits.
