The playlist import that died three methods deep

Objectives

  • Read a stack trace from the method that threw back to main()
  • Explain how an uncaught exception travels up the call stack to the calling method
  • Choose the method where catching an exception makes sense, and leave the others alone

Requirements

  1. R1 Inside the loop of importPlaylist(), the call to parseTrack() is in a try block. A catch block for NumberFormatException prints Skipped line N: <line> (N counts from 1) and the loop continues.
  2. R2 parseTrack() and parseDuration() contain no try or catch. The exception travels up to importPlaylist().
  3. R3 No printStackTrace() is left in the finished code.
  4. R4 Running the test program prints exactly what it expects. (verified by the program output)

Before you code: warm-up and model answers

  1. Read the trace in the brief from the top at Playlist... line down. Which method threw the exception, and in what order were the methods called?

    parseDuration() threw it (line 25, parseInt on "4x"). main() called importPlaylist() (TestPlaylist.java line 11), which called parseTrack() at line 10, which called parseDuration() at line 18. The trace lists them in reverse: the most recent call is on top, and the java.base lines above them are inside parseInt().

  2. If you wrapped the whole for loop in a try block instead of just the call, what total would the import report? Why?

    7 min 35 s: only the first two tracks (210 + 245 = 455 seconds). The exception at line 3 abandons the try block, and the loop is inside it, so Home Stretch is never read.

Solution

Playlist.java
public class Playlist
{
    // Each line looks like "Title|m:ss". Returns the total length in seconds.
    public static int importPlaylist(String[] lines)
    {
        int total = 0;
        for (int x = 0; x < lines.length; ++x)
        {
            try
            {
                total += parseTrack(lines[x]);
            }
            catch (NumberFormatException e)
            {
                System.out.println("Skipped line " + (x + 1) + ": " + lines[x]);
            }
        }
        return total;
    }

    public static int parseTrack(String line)
    {
        int bar = line.indexOf('|');
        return parseDuration(line.substring(bar + 1));
    }

    public static int parseDuration(String time)
    {
        int colon = time.indexOf(':');
        int minutes = Integer.parseInt(time.substring(0, colon));
        int seconds = Integer.parseInt(time.substring(colon + 1));
        return minutes * 60 + seconds;
    }
}

Walkthrough

Integer.parseInt("4x") throws a NumberFormatException in parseDuration(). No method catches it, so it travels up the call stack: to parseTrack(), then importPlaylist(), then main(), then the JVM, which prints the trace and stops (pp. 415–417). The trace lists those calls from the top (where it was thrown) to the bottom (where it started), with a line number for each. Catching in parseDuration() would force it to invent a value such as 0, which hides the error; catching in main() would stop the import at the bad line. importPlaylist() knows the line and its number, so it can skip just that track. The try block must be inside the loop: a try block around the whole loop ends the import at line 3 and loses Home Stretch (the total becomes 7 min 35 s). printStackTrace() is useful while debugging but doesn't belong in a finished program (p. 417). Catching IllegalArgumentException, the parent of NumberFormatException, also passes.

Messages students see when a check fails

C1 · The call is tried inside the loop

Put the try block inside the for loop, around total += parseTrack(lines[x]);. Then a bad line abandons only its own iteration and the loop moves to the next track.

C2 · A catch block skips the bad line

Add catch (NumberFormatException e) after the try block and print Skipped line N: followed by the line. Integer.parseInt() throws that type for 4x.

C3 · parseDuration() lets the exception travel up

Leave parseDuration() without try or catch. It can't know whether a bad duration should be skipped, fixed or reported, so it lets the exception go to the method that called it.

C4 · parseTrack() lets the exception travel up

Leave parseTrack() without try or catch, too. The exception should pass through it to importPlaylist(), which knows the line number.

C5 · No stack trace in the finished program

Remove printStackTrace(). It is a good tool while you develop (p. 417), but a user importing a playlist only needs to know which line was skipped.

Progressive hints

  1. Use the trace: list the methods it passes through and ask, for each one, “does this method know enough to skip one track?”

  2. The method that knows the line number is the one with the loop.

  3. Where the try block starts matters. It has to restart for each line, so it belongs inside the loop's braces.

Reflection: questions and model answers

  1. Why is parseDuration() the wrong place to catch the exception, even though that is where it happens?

    parseDuration() only sees "3:4x". To catch there it would have to return some number, such as 0, which silently adds a wrong track length. It doesn't know the line or what the user wants, so it should let the exception travel up.

  2. The book says cycling through the stack has an advantage and a disadvantage (p. 417). Name both, using this program.

    Advantage: each exception can be handled wherever it makes most sense, here in importPlaylist(). Disadvantage: in a larger program the place where an exception is caught can be far from where it started, so you need the trace to find the real source (parseDuration).
