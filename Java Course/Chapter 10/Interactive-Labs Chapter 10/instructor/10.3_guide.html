The bill splitter that won't compile

Objectives

  • Follow one try block with several catch blocks, each with its own response
  • Order catch blocks from specific to general so none of them is unreachable
  • Explain why only the first failing statement in a try block throws

Requirements

  1. R1 A catch (ArithmeticException ...) block sets the result to Enter at least 1 person.
  2. R2 A catch (NumberFormatException ...) block sets the result to Use whole numbers, like 84.
  3. R3 The general catch (Exception ...) block stays, as the last catch block, so the file compiles.
  4. R4 Running the test program prints exactly what it expects. (verified by the program output)

Before you code: warm-up and model answers

  1. Read the compiler error in the brief. Why does Java refuse a catch block for ArithmeticException after a catch block for Exception?

    An ArithmeticException is an Exception, so the first block would always catch it. The second block can never run; it is unreachable, and Java treats unreachable code as an error (p. 406).

  2. Once it compiles, what will split("ten", "0") return: the message about people or the one about whole numbers? Why?

    The whole-numbers message. parseInt("ten") throws first, the rest of the try block is abandoned, and the division by 0 never happens.

Solution

BillSplitter.java
public class BillSplitter
{
    // Splits a bill typed into the app. Amounts are whole dollars.
    public static String split(String billText, String peopleText)
    {
        String result;
        try
        {
            int bill = Integer.parseInt(billText);
            int people = Integer.parseInt(peopleText);
            int each = bill / people;
            int left = bill % people;
            result = "$" + each + " each, $" + left + " left for the tip jar";
        }
        catch (ArithmeticException e)
        {
            result = "Enter at least 1 person";
        }
        catch (NumberFormatException e)
        {
            result = "Use whole numbers, like 84";
        }
        catch (Exception e)
        {
            result = "Something went wrong";
        }
        return result;
    }
}

Walkthrough

Catch blocks are examined in order, and the first one whose type matches runs (p. 404). Exception matches every exception here, so a block for it placed first makes every later block unreachable, and the compiler rejects the file with “has already been caught” (p. 406). Put the “smaller baskets” first: ArithmeticException and NumberFormatException are unrelated (neither extends the other), so their order doesn't matter, but Exception must come last. For split("ten", "0") only parseInt("ten") throws: the try block is abandoned before the division, so the message is about whole numbers (p. 404). Note for instructors: the multi-catch on p. 407 is printed with a comma; Java (since Java 7) writes it catch (ArithmeticException | InputMismatchException e).

Messages students see when a check fails

C1 · A catch block for ArithmeticException

Keep a catch (ArithmeticException e) block and give it its own message for a party of 0. Dividing by 0 people is the only thing that throws this type here.

C2 · A catch block for NumberFormatException

Add a catch (NumberFormatException e) block. Integer.parseInt() throws it when the text isn't a whole number, such as 84.50 or ten.

Hint:

Which statements in the try block convert text to numbers?

C3 · The general catch block comes last

Keep catch (Exception e) as the safety net, but move it below the specific blocks. A general block in front of a specific one makes the specific one unreachable, and the file won't compile.

Progressive hints

  1. Read the error again: which block is in the way of which?

  2. Two different statements can fail with two different types: the conversions and the division. Each type gets its own block.

  3. Think of the blocks as baskets from the smallest to the biggest (p. 406): an exception falls past the ones that don't fit until one holds it. The biggest basket goes at the bottom.

Reflection: questions and model answers

  1. Does it matter whether the ArithmeticException block or the NumberFormatException block comes first? Explain using the class hierarchy.

    No. Neither class extends the other (ArithmeticException and NumberFormatException are separate RuntimeExceptions), so neither can catch the other's exceptions. Order only matters between a class and its own ancestors, such as Exception.

  2. With specific blocks in place, is the catch (Exception e) block still worth keeping? Give a reason for or against.

    For: it keeps the app running if a later change adds a statement that throws something unexpected. Against: it hides bugs behind a vague message, so it should at least log what it caught. Either answer is fine with a reason.
