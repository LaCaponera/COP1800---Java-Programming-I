The hold shelf that only takes books

Objectives

  • Declare a generic class with a type parameter section, class Slot<T>
  • Use the type parameter T for a field, a parameter and return types
  • Instantiate the same generic class with different reference types, and explain why a primitive can't be used

Requirements

  1. R1 The class header declares a type parameter: public class Slot<T>.
  2. R2 The field, the parameter of put() and the return types of peek() and take() use T; Slot mentions neither Book nor Object.
  3. R3 put() returns false and changes nothing when the slot is already full. take() returns the item and leaves the slot empty (null).
  4. R4 Running the test program prints exactly what it expects. (verified by the program output)

Solution

Slot.java
// One cubby on the library's hold shelf. It holds one item of any type.
public class Slot<T>
{
    private T item;

    // Puts an item in an empty slot. Returns false if the slot is taken.
    public boolean put(T newItem)
    {
        if (item != null)
            return false;
        item = newItem;
        return true;
    }

    // Returns the item without removing it (null if the slot is empty).
    public T peek()
    {
        return item;
    }

    // Removes and returns the item (null if the slot is empty).
    public T take()
    {
        T taken = item;
        item = null;
        return taken;
    }

    public boolean isEmpty()
    {
        return item == null;
    }
}

Walkthrough

A generic class is declared like any class, but the class name is followed by a type parameter section in angle brackets (p. 530). T stands in for whatever reference type the program supplies, so Slot<Book> gets a Book field and peek() returns a Book. That's why the test can call shelfA.peek().getTitle() with no cast, as bookObj.getObject().getTitle() does in Figure 13-27. A type parameter can't be a primitive such as int (p. 530), so the locker code uses Slot<Integer>; Java wraps 4821 in an Integer when it is put in and unwraps it when it is assigned to int code. In take(), the item must be saved in a local variable before the field is set to null, or the method would return null. An Object field would also hold anything, but then every caller would need a cast and the compiler couldn't stop a laptop going into a book slot.

Messages students see when a check fails

C1 · Slot has a type parameter

Change the header to public class Slot<T>. The angle brackets after the class name are the type parameter section.

C2 · The field and methods use T

Use T for the field (private T item;), for the parameter of put(T newItem) and as the return type of peek() and take().

C3 · No Book or Object left in Slot

Replace every Book in Slot.java with T. With Object instead of T, every caller would need a cast and anything could go in any slot.

C4 · A full slot refuses a second item

At the top of put(), return false when item != null. Only an empty slot accepts an item.

C5 · take() empties the slot

In take(), save the item in a local T variable, set the field to null, then return the saved item.

Reflection: questions and model answers

  1. A teammate says, "Just make the field an Object; it can hold anything too." Using shelfA.peek().getTitle() from the test program, explain what the generic version gives you that the Object version doesn't.

    With Slot<Book>, peek() returns a Book, so getTitle() compiles with no cast, and the compiler refuses a Laptop in a book slot. With Object, peek() returns Object, so each caller must cast, and a wrong type is found only when the program crashes.

  2. Why does take() need a local variable, and what would the test print for Picked up: without it?

    The field must be set to null to empty the slot, but the item still has to be returned, so it is saved first. Returning after setting the field to null would return null, and getTitle() would throw a NullPointerException.
