Comments that help, comments that hide

Objectives

  • Write the header comments every class file should begin with
  • Use a block comment to describe a class's purpose
  • Comment out a statement so it no longer executes, without deleting it
  • Explain how a misplaced block comment changes what runs

Requirements

  1. R1 The file starts with three line comments: // Filename ShiftReminder.java, // Written by <your name>, // Written on <today's date>.
  2. R2 Right after the class header's opening brace, a block comment of at least two lines (/* ... */) describes what the class does.
  3. R3 The debug statement is commented out, not deleted, so it doesn't execute.
  4. R4 The break and lunch times print again: the note about them stays a comment, but the statements run.
  5. R5 The staff screen shows exactly the five lines above. (verified by the program output)

Before you code: warm-up and model answers

  1. Before changing anything, predict what the starter prints. Which statements in main() will not run, and why?

    It prints the DEBUG line, the reminder, the doors line and the badge line. The Break and Lunch statements don't run because they are between /* (on the note line) and */ (after the Lunch statement), so the compiler treats them as part of a block comment.

  2. Java has three kinds of comments. Name them and the symbols that start (and, where needed, end) each one.

    Line comments start with // and run to the end of the line. Block comments start with /* and end with */, across any number of lines. Javadoc comments start with /** and end with */ and are used to generate documentation.

Solution

ShiftReminder.java
// Filename ShiftReminder.java
// Written by Alex Rivera
// Written on September 4
public class ShiftReminder
{
    /* This class prints the reminder that staff see before the
       Saturday shift: opening time, break times and badge rule. */
    public static void main(String[] args)
    {
        // System.out.println("DEBUG: reminder program started");
        System.out.println("Reminder for the Saturday shift");
        System.out.println("Doors open at 7:00 AM");
        // Break times were moved by the manager on May 3
        System.out.println("Break: 10:30 AM (15 minutes)");
        System.out.println("Lunch: 12:30 PM (30 minutes)");
        System.out.println("Bring your badge to clock in");
    }
}

Walkthrough

Comments are nonexecuting: the compiler skips everything from // to the end of a line, and everything between /* and the next */, however many lines that is. In the starter, the note about break times opened a block comment that wasn't closed until after the Lunch statement, so both statements became part of the comment. The program still compiled, which is what makes this mistake hard to spot. A line comment on the note (or closing */ on the same line) fixes it.

Messages students see when a check fails

C1 · Header comment lines sit above the class

Above public class ShiftReminder, add three line comments: the file name, your name and the date, each starting with //. These checks can't read comments, so this one only confirms that three comment lines are there.

C2 · A comment of two or more lines follows the class header

Between the class's opening brace and the main() header, add a block comment that starts with /*, describes what the class does in at least two lines, and ends with */.

C3 · The debug line no longer executes

Turn the debug statement into a comment by putting // at the start of its line. The statement stays in the file for later, but the compiler no longer translates it.

C4 · The break and lunch statements execute

The Break and Lunch statements are inside a block comment: it starts with /* on the note line and doesn't end until the */ after Lunch. Make only the note a comment, so both statements run again.

Hint:

Find the /* and then find the first */ after it. Everything between them is a comment, whatever it looks like.

C5 · The reminder lines print in order

Keep the order of the staff screen: reminder, doors, break, lunch, badge.

Progressive hints

  1. Section 1.7's "You Do It" shows the exact shape of the three header comments. They go at the very top of the file, before the class header.

  2. A comment that turns off a statement is a line comment placed at the start of that statement's line. Only that one line is affected.

  3. For the missing times, find where the block comment begins and where it ends. How many statements are between the two markers?

Reflection: questions and model answers

  1. Why is commenting out the debug statement better here than deleting it? Describe a situation where commenting out a statement helps you find a bug.

    Commenting it out stops it from running but keeps the code, so the developer can turn it back on later by removing the //. When a program misbehaves, you can comment out statements one at a time and rerun it to see which one causes the problem, then restore the others.

  2. The missing break times caused no compiler error. Why not, and what habit would prevent this mistake?

    Everything between /* and */ is a legal comment, so the compiler simply skipped the two statements; the program was still valid Java. Prevent it by closing every block comment on purpose (check that each /* has its */ where you intend), using // for one-line notes, and checking the output after editing.

Extension

Add a Javadoc comment (/** ... */) above main() that describes it in one sentence. Look in Appendix E or the Javadoc documentation to find out what the @param tag is for.
