The swim school's two sets of rules

Objectives

  • Use decisions in a set method to keep a field's value within the allowed range
  • Have a constructor call the set methods so each rule is written once
  • Test the parameter (the new value), not the field (the old value), in a setter's decision

Requirements

  1. R1 The constructor contains no decisions: it calls setStudentId() and setAge() with its parameters.
  2. R2 setAge() decides using the parameter studentAge: from MIN_AGE to MAX_AGE it is stored, otherwise age becomes 0.
  3. R3 Running the test program prints exactly what it expects. (verified by the program output)

Before you code: warm-up and model answers

  1. The constructor and setAge() both check ages. Find one age they disagree about, and say what each would store.

    Age 2 (anything under 4): the constructor checks only studentAge <= MAX_AGE, so it stores 2; setAge(2) checks the minimum too and would store 0.

  2. When mia.setAge(21) runs in the starter, Mia's age field is 10. Is the if true or false, and what does age become?

    True: the condition tests the field, and 10 is between 4 and 17. So age = studentAge; runs and stores 21, which breaks the rule.

Solution

SwimStudent.java
public class SwimStudent
{
    private int studentId;
    private int age;
    public final int MAX_ID = 9999;
    public final int MIN_AGE = 4;
    public final int MAX_AGE = 17;

    public SwimStudent(int id, int studentAge)
    {
        setStudentId(id);
        setAge(studentAge);
    }

    public void setStudentId(int id)
    {
        if(id <= MAX_ID)
            studentId = id;
        else
            studentId = 0;
    }

    public void setAge(int studentAge)
    {
        if(studentAge >= MIN_AGE && studentAge <= MAX_AGE)
            age = studentAge;
        else
            age = 0;
    }

    public int getStudentId()
    {
        return studentId;
    }

    public int getAge()
    {
        return age;
    }
}

Walkthrough

Two copies of a rule drift apart: the constructor's age check had no minimum, so a 2-year-old was enrolled, while the setter had one. When the constructor calls setStudentId(id) and setAge(studentAge), each rule exists exactly once, in the method whose job is to guard that field, and a future change (say, a maximum age of 18) is made in one place (Figure 5-36). The setter's decision must test the new value, the parameter studentAge. The starter tested the field age, the value already stored: for a new object that is 0, so every age was refused, and for Mia (age 9) the test passed for any new value, which is how 21 got in. The book's own Figure 5-36 contains the same slip: its setPayRate() tests payRate instead of rate.

C1 · The constructor calls the setters and makes no decisions

Replace the constructor's if statements with calls to setStudentId(id) and setAge(studentAge). The rules are then written once, in the setters, and the constructor can never disagree with them again.

Reflection: questions and model answers

  1. Riptide raises the maximum age to 18. With your solution, how many places must change? How many with the starter?

    One: the MAX_AGE constant, used only by setAge(). With the starter the rule lived in the constructor and in the setter, so both would have to be found and changed, and missing one recreates the inconsistency.

  2. Look at setPayRate() in the book's Figure 5-36. Using what you fixed here, what does its if test, and what pay rate would new Employee(1234, 75.00) end up with?

    It tests the field payRate, not the parameter rate. For a new object payRate is 0.0, so 0.0 <= MAX_RATE is true and 75.00 is stored, above the $60 limit; the rule never actually checks the new rate.
