COP1800 · Java Programming I · Lab 9.9

The water alert that skipped the phone app

Objectives

  • Assign subclass objects to a superclass reference
  • Write a method with a superclass parameter that works for every subclass
  • Explain dynamic method binding: the object, not the variable's type, decides which method runs

Requirements

  1. R1 AlertCenter.alert() sends the alert by calling send() on the Notifier it receives, with no instanceof tests and no channel-specific text.
  2. R2 Every alert's message starts with [City Water] (with a space after the bracket).
  3. R3 Running the test program prints exactly what it expects. (verified by the program output)

Before you code: warm-up and model answers

  1. Notifier third = new PushNotifier("Lena"); compiles even though Notifier is abstract. What kind of object does third refer to?

    A PushNotifier. The variable's type is Notifier, but the object is a concrete PushNotifier; a Notifier reference can hold any subclass object.

  2. Read the starter's alert(). What does it return for the push notifier, and why?

    “No channel for Lena”. It only tests for EmailNotifier and SmsNotifier, so a PushNotifier falls through to the else branch.

Starter files

AlertCenter.java
public class AlertCenter
{
    // Sends one city alert through whatever channel the notifier uses.
    // Every alert starts with "[City Water] ".
    public static String alert(Notifier n, String message)
    {
        // TODO (R1, R2): this rebuilds each channel's text by hand and
        // forgets the prefix. It breaks whenever a channel changes or a
        // new one is added.
        if (n instanceof EmailNotifier)
            return "Email to " + n.getRecipient() + ": " + message;
        else if (n instanceof SmsNotifier)
            return "SMS to " + n.getRecipient() + ": " + message;
        else
            return "No channel for " + n.getRecipient();
    }
}
Notifier.java (read-only for students)
public abstract class Notifier
{
    private String recipient;

    public Notifier(String to)
    {
        recipient = to;
    }

    public String getRecipient()
    {
        return recipient;
    }

    // Each channel formats and sends the message in its own way.
    public abstract String send(String message);
}
EmailNotifier.java (read-only for students)
public class EmailNotifier extends Notifier
{
    public EmailNotifier(String address)
    {
        super(address);
    }

    @Override
    public String send(String message)
    {
        return "Email to " + getRecipient() + ": " + message;
    }
}
SmsNotifier.java (read-only for students)
public class SmsNotifier extends Notifier
{
    public SmsNotifier(String phone)
    {
        super(phone);
    }

    // The carrier asked us to call these "texts" (changed in May).
    @Override
    public String send(String message)
    {
        return "Text to " + getRecipient() + ": " + message;
    }
}
PushNotifier.java (read-only for students)
public class PushNotifier extends Notifier
{
    public PushNotifier(String userName)
    {
        super(userName);
    }

    // New this week: alerts in the city's phone app.
    @Override
    public String send(String message)
    {
        return "Push to " + getRecipient() + "'s phone: " + message;
    }
}

Solution

AlertCenter.java
public class AlertCenter
{
    // Sends one city alert through whatever channel the notifier uses.
    // Every alert starts with "[City Water] ".
    public static String alert(Notifier n, String message)
    {
        return n.send("[City Water] " + message);
    }
}

Walkthrough

Every subclass object “is a” superclass object, so a Notifier reference can hold an EmailNotifier, an SmsNotifier or a PushNotifier, even though Notifier is abstract (p. 359). When n.send(...) runs, Java chooses the send() of the object n currently refers to: dynamic (late) method binding (p. 360). That makes a superclass parameter the natural design, like talkingAnimal(Animal animal) in Figure 9-38 (p. 360): the method works for every present and future subclass. The last two lines of the test show the same variable channel calling two different send() methods, like animalRef.speak() in Figure 9-36 (p. 359).

Messages students see when a check fails

C1 · alert() lets the notifier send

Return n.send(...). Each notifier already knows how to format its message; Java picks the right send() for the object while the program runs.

C2 · No type tests or copied channel text

Remove the instanceof chain and the hand-built text. With them, every new or changed channel needs an edit here; without them, alert() works for any Notifier.

C3 · Every alert has the [City Water] prefix

Pass "[City Water] " + message to send(), so every channel receives the prefix.

Progressive hints

  1. Every Notifier, whatever its subclass, has a send(String) method. Which object do you have in alert()?

  2. The whole method body can be one return statement.

  3. Build the prefixed text first, then hand it to n.send(...).

Reflection: questions and model answers

  1. Next month the city adds a VoiceCallNotifier. What has to change in your alert(), and what would have had to change in the starter's?

    Nothing changes in my alert(), because it calls send() on any Notifier and dynamic binding runs the new class's send(). The starter would need another instanceof branch with copied text, or voice calls would get “No channel”.

  2. In channel.send(...), the variable's type is Notifier both times. What decides which send() runs, and when is that decided?

    The type of the object the variable refers to at that moment decides it, and it is decided while the program runs, not when it compiles. That is dynamic method binding.
