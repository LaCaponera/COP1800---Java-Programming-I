COP1800 · Java Programming I · Lab 3.6

The outfitter's sale tags

Objectives

  • Overload a method by giving the same name different parameter lists
  • Predict which version runs from the types of the arguments in a call
  • Divide by 100.0, not 100, to turn a whole-number percent into a fraction
  • Explain when one overloaded name is easier to use than several different names

Requirements

  1. R1 Add an overload displaySalePrice(double price, int percent) that treats the int as a whole-number percent, dividing by 100.0 so the fraction keeps its decimals.
  2. R2 Add an overload displaySalePrice(double price) that applies the 10% member discount from a named constant MEMBER_PERCENT, and print a member's tag for the $80.0 item from main().
  3. R3 All three versions share the name displaySalePrice and print the same tag format.
  4. R4 The tags match the screen above, and so do the test program's three tags for a $200.0 item. (verified by the program output)

Before you code: warm-up and model answers

  1. Predict the starter's tag for displaySalePrice(80.0, 25) and explain how Java arrives at it.

    Sale price of $80.0 is $-1920.0. The int 25 is promoted to 25.0 to fit the double parameter, so the method computes 80 - 80 x 25 = -1920.

  2. Once both overloads exist, which version runs for each call: displaySalePrice(80.0, 0.25), displaySalePrice(80.0, 25) and displaySalePrice(80.0)?

    The first runs (double, double) because 0.25 is a double; the second runs (double, int) because 25 is an int and that version is an exact match; the third runs (double), the only version with one parameter.

Solution

SaleTags.java
public class SaleTags
{
    public static void main(String[] args)
    {
        displaySalePrice(80.0, 0.25);   // rate as a fraction
        displaySalePrice(80.0, 25);     // a manager typed a whole percent
        displaySalePrice(80.0);         // a member's tag
    }

    public static void displaySalePrice(double price, double rate)
    {
        double salePrice = price - price * rate;
        System.out.println("Sale price of $" + price + " is $" + salePrice);
    }

    public static void displaySalePrice(double price, int percent)
    {
        double rate = percent / 100.0;
        displaySalePrice(price, rate);
    }

    public static void displaySalePrice(double price)
    {
        final int MEMBER_PERCENT = 10;
        displaySalePrice(price, MEMBER_PERCENT);
    }
}

Walkthrough

The compiler picks the version whose parameter list matches the arguments: 0.25 is a double, so (double, double) runs; 25 is an int, and (double, int) is an exact match, so it wins over promoting 25 to double; a single argument can only match (double). Dividing by 100.0 matters: 25 / 100 is integer division and gives 0. The int and one-argument versions hand the work to the (double, double) version, so the formula and the tag format live in one place. Writing each version's own arithmetic also passes, as long as the tags match.

Messages students see when a check fails

C1 · An overload takes (double, int)

Add a second method named displaySalePrice whose parameter list is a double followed by an int. Same name, different parameter types: that is an overload, and the compiler chooses it whenever the second argument is an int.

C2 · The percent is divided by 100.0

Turn the percent into a fraction by dividing by 100.0, not 100. Two integers divide to a truncated integer, so 25 / 100 is 0 and the tag would show no discount at all.

Hint:

Try System.out.println(25 / 100); and then System.out.println(25 / 100.0);.

C3 · An overload takes only the price

Add a third displaySalePrice with a single double parameter for the price. A call with one argument can only match this version.

C4 · The member discount is a named constant

Declare the member discount as a named constant, MEMBER_PERCENT, holding 10, and use it in the one-argument version.

C5 · main() prints a member's tag

Print the member's tag from main() by calling displaySalePrice with the price 80.0 alone.

C6 · All three versions share one name

Name every version displaySalePrice. Callers then remember one name and pass whatever they have, and the compiler chooses the version from the arguments.

Progressive hints

  1. Run the starter. The second tag is wrong because 25 was promoted to double and used as if it meant 0.25. What would make Java choose a different method when the second argument is an int?

  2. An overload keeps the name and changes the parameter list. The int version can turn the percent into a fraction and hand the rest of the work to the version that already exists.

  3. In Java, 25 / 100 is 0. At least one of the two numbers must be a double for the division to keep its decimals.

Reflection: questions and model answers

  1. You could have named the methods displaySalePriceFraction, displaySalePricePercent and displayMemberPrice. Give one reason overloading is better here, and one situation where separate names would be clearer.

    Overloading lets callers remember one name for the same task and pass whatever they have; the compiler picks the right version. Separate names are clearer when the methods do genuinely different jobs: overloading suits tasks that are functionally identical apart from the argument types.

  2. Suppose the int and one-argument versions call the (double, double) version instead of repeating the arithmetic. What is gained if the store later rounds every sale price down to the nearest dollar?

    The rounding is added in one place, the (double, double) version, and every overload picks it up because they all funnel into it. With three separate formulas, three methods would need the same change and could drift apart.
